# User-interface contract

This page keeps the durable user-visible rules. The selected backend's capability catalog determines which product areas are available. Exact geometry, event ordering, and regression assertions belong in the current browser and Node tests.

## Supported runtime

Go owns the supported runtime. Shared browser shells and saved layout aliases do not establish that a server feature exists. Search & Runs event search and run history, background AI activity summaries, watched pull requests, and hosted GitHub/Linear enrichment are retired. Native chat, agent conversations, terminal transcripts, local Finder/Git views, and per-session event logs retain their own capability and route owners. Mock interactive clients retain complete Unicode characters during key-by-key input, matching the real client composer. The current route and retirement inventory is in [`GO_MIGRATION.md`](../../GO_MIGRATION.md).

## Authentication setup

- On first Go startup, create `auth.yaml` in the configured directory with mode 0600, a generated admin password, and the account entry commented out. The first-run page points to this file and tells the user to uncomment the existing admin entry; it never displays the generated password. Preserve any existing auth file. Existing empty or placeholder configurations receive instructions for adding an admin account or replacing placeholder credentials instead of assuming a generated account exists.

## Software updates

- The update notice appears after an eligible `version.yaml` bump reaches `origin/main`; ordinary commits without a higher product version stay silent. The configured major/minor/patch/none preference controls notices, and `none` disables update checks.
- Only an admin can start Update & restart. Confirmation precedes installation, and readonly users cannot submit the mutation. A repeated admin click returns the active job instead of starting another installer.
- The server prepares the exact fetched commit before activation. Dirty, diverged, or changed checkouts remain untouched. Preparation errors keep the current server running and remain visible in job status.
- A browser reload waits for both the target product version and a different Go instance identity. An old server response cannot complete restart polling; unsaved editor changes and active typing continue to defer reload.

## Layout and navigation

- Back and Forward traverse one global, unique list of visited tab instances across all panes. Explicit tab activation and pane-body focus move that tab to the end; traversal preserves recency and never reopens a closed tab. Clicking after Back retains all other surviving entries. History lasts until page reload and retains every visited open tab, including distinct copies. In Normal mode, traversal reveals a visited tab even when it is registered outside the current single-pane layout, without recording another visit.
- Closing the focused tab selects and focuses the globally most recently visited survivor, even after Back; closing a background tab preserves focus. Reconcile batch removals before selecting a replacement, including external tmux exits and tab-cap eviction. If no visited tab survives, choose the first remaining tab in layout order. Moves, reorder, pinning, and rendering do not record visits; renames replace IDs in place. Explicit navigation and closure focus content with automatic cursor following disabled, and stale callbacks cannot override newer focus.
- Finder deletion keeps unsaved buffers open while requests are pending and after failures. A successful deletion retains dirty content as missing on disk, including edits typed while the request was pending; only successfully deleted clean tabs close.

- Keep panes and tabs usable across desktop, narrow-window, and touch layouts. Preserve the user's active selection and restored layout when switching between surfaces.
- A settings save preserves the layout and focused pane selected when its response arrives. Navigation admitted while the request is in flight must remain visible after the settings apply.
- When switching Tabber from Normal to Advanced, retain Tabber as the selected home tab if it was active before the switch.
- Pane header buttons and tab-close controls use the same dimensions and styling on mobile, touch, and desktop layouts. Do not enlarge their hit targets or header rows for touch; native touch taps use the same actions as desktop clicks.
- When a tmux session exits outside YOmux, remove its tab and reconcile its pane within five seconds while preserving the saved layout placeholder.
- Session rename accepts one submission while its reply is pending. The submit button visibly disables, the existing tab displays the proposed name, and rejection restores the original name and re-enables submission. Accepted renames preserve the new tab, active pane, and roster when an older roster arrives.
- When a tmux session is renamed outside YOmux, preserve its tab and pane under the new name even if metadata or activity reaches the browser before the roster event.
- A control's label, tooltip, accessibility state, and action must agree. Menus and popovers must work with pointer, keyboard, and focus changes. Checked actions that keep a menu open refresh their state without closing its submenu or losing focus.
- The Tabber New Chat menu escapes pane clipping while remaining anchored to its trigger and bounded by the visible viewport.
- Shared browser code does not imply that every backend supports every route. Hide or disable features according to `/api/capabilities`.

## Terminal and status

- Terminal file references remain one target across xterm soft wrapping and Codex indented word wrapping, including splits before the right edge and prose after the filename. Right-clicking any painted segment offers the complete path; Open file selects that file in the editor. Blank rows, closing delimiters, and new absolute paths stop continuation.
- Preferences ends with Enable experimental features, off by default. Enabling it adds YO!chat, YO!agent, and YO!info to File and Tabs, including already-open views; disabling it hides those menu entries without closing views. Changes apply live and persist across reloads.
- Menus show available keyboard shortcuts on the right, aligned with the label on one row, using platform-appropriate keys; command palette entries reuse the same shortcut metadata. File navigation and keyboard help name Finder/File Explorer and Tabber in Normal mode, adding Differ only in Advanced mode. Labels update when the mode changes.
- Letter shortcuts follow the active keyboard layout. Dvorak Cmd+C copies selected text in Markdown editors and terminals; Dvorak Cmd+I italicizes editor text. Modified symbol shortcuts retain their base-key handling.
- Mouse-reporting terminal panes use xterm's negotiated mouse protocol for ordinary desktop wheel input and preserve native Page Up/Down bytes. This path works without the optional Tmux diagnostics snapshot. Existing Codex/OpenCode scroll controls keep their explicit application routes. Shift+wheel and Shift+Page Up/Down select tmux history. Claude keeps its conversation history inside the application while using an alternate screen; tmux copy mode can therefore show 0/0 even when Claude has older messages. Use ordinary scrolling or unshifted Page Up/Down (Fn+Up/Down on Mac) for that conversation, and Esc to leave tmux copy mode.
- Terminal input, selection, copy, paste, links, and touch gestures must preserve the terminal application's own behavior where it owns the interaction. Keyboard delivery must remain available during resize, attach, and secondary pane updates. Network ping is distinct from native-key-to-visible-character latency.
- In Codex panes, ordinary wheel and trackpad scrolling moves through the conversation while keeping the prompt fixed. YOmux delivers server-generated mouse reports as literal input to the validated live pane. Page Up/Down (Fn+Up/Down on Mac) sends native application keys and also scrolls the Codex conversation. These application-scroll actions are passive: they do not acknowledge attention or record typing, and they leave copy mode before delivery. Shift+wheel and Shift+Page Up/Down scroll tmux history instead; Esc exits copy mode, and ordinary application scrolling returns to Codex. The Keyboard Shortcuts and Legends popup must explain this distinction and identify Fn+Up/Down on Mac.
- Terminal resizing uses native tmux copy-mode reflow. YOmux does not reposition copy cursors during resize; native reflow may move the scrolled viewport, including to the bottom. Navigation from another browser, server, or native tmux client remains authoritative.
- Terminal URL and file-reference discovery stays within the visible viewport and at most 64 physical rows per wrapped token. Redraw scheduling does no buffer scans, and a token that crosses the row limit remains unlinked. Right-click URL actions preserve every character through tmux soft wraps and supported CLI hanging indents and gutters, including query and fragment delimiters; following independent text stays outside the URL. Hover, Open URL, and Copy URL use terminal cell widths for wide characters, surrogate pairs, and combining marks.
- Explicit terminal hyperlinks use xterm's retained target and cell ranges for hover discovery, Open URL, and Copy URL, including labels that differ from their destination. Explicit targets take precedence over overlapping text guesses. Text-only Codex and Claude continuations share one rule in both traversal directions; OpenCode gutter rules apply only to its registered layout. Indentation changes, unrelated prose, and independent following URLs end a continuation. Left-click behavior stays unchanged.
- Agent status comes from the selected pane or window. Exclude verified internal Tabber window-view aliases from process attribution so activity stays keyed to the source session. Do not create duplicate rows or carry activity across a reused tmux target.
- A visible Codex `Working (... esc to interrupt)`, `Compacting context (...)`, or `Waiting for background terminal (...)` line is the current working state, even when the idle composer and older command output remain on screen. Spinner animation phases must not change that state. Codex temporarily hides its working row while streaming commentary; process-owned history keeps that active turn working. Read legacy rollout turn/item events or the exact process-held writer thread in paginated SQLite history; never choose a different thread by recency. Read only a bounded suffix, ignore partial records and records older than the current process, and keep an ambiguous composer unavailable when history evidence is missing. Explicit completion screens remain valid through acknowledgement and cooldown expiry. Claude's current interrupt control below its ruled composer means working in manual, plan, auto, accept-edits, and bypass modes, regardless of the animated activity verb. Quoted controls and complete code examples do not count; an unmatched fence in tool output cannot hide live client chrome.
- Repository carousel Next and Previous controls advance from the checkout currently displayed, including the active checkout selected by default. They wrap at either end and retain an explicit selection until the user changes it.
- Pane Tabs, Tabber, Info groups, window controls, and status popovers share compact 9 CSS-pixel status slots, glyph geometry, outlines, semantic colors, animation, and acknowledgment. Activity precedes status badges; agent identity icons remain adjacent; no surface scales its status glyph independently. Pane Tabs and Tabber show Play for green working, Pause for yellow completion, and a square Stop for red attention or blocked status when there is only one distinct visible status color, regardless of window count. Single-color symbols have a thin dark outline so their edges remain visible on matching colored tab backgrounds. Red attention, blocked, and unavailable states share one color. Mixed status colors retain segmented circles, including green with red or yellow. Preserve indicator spacing, status badges, accessibility labels, and pulse animation through these transitions.
- Agent windows pulse green while working. Successful status scans keep working indicators visible through the next scheduled scan and its bounded collection window. A committed status change refreshes the shared cache independently of statistics graph backfills; unavailable results retry promptly. Cached working state expires even if the background projection stops refreshing. A metadata refresh must keep that pulse when a fresh collector sample matches the current session, pane, agent kind, and process instance; metadata expiry alone does not mean work stopped. After a status sample confirms that work stopped and the agent is idle, pulse yellow for the configured workflow transition duration, then keep a steady yellow completion reminder until the user acknowledges it or a new run begins. Yellow means the agent stopped working and the user can type; the animation timer must not remove the reminder.
- Session summaries reduce distinct physical windows through the same agent-window model; multiple repository records for one window count once. Same-kind sibling agents remain separate, so a working window cannot hide a blocked sibling. Authoritative empty inventories and unavailable samples never fall back to stale agent metadata. Connection, active test commands, and repository readiness remain separate facts.
- The backend owns agent working state. Pane Tabs, Tabber rows in both modes, window controls, and live counters consume the same admitted agent-window snapshot and shared display update. An accepted SSE or activity response updates all mounted indicators and Tabber dates together. A newer unavailable sample must not inherit an earlier working state; metadata and historical activity dates do not override current backend state.
- Detect current requests for user input or approval and blocked/error screens automatically, including untouched and hidden tabs. Show a red `ASK` for a recognized question or approval request and a red `BLK` for a blocker. A queued Codex question may show red `ASK` beside a green working ball because the agent is still running. Match current prompt controls and screen evidence; quoted questions and older output must not create attention. URL query delimiters, including a hard-wrapped URL row ending in `?`, and fenced code must not create ASK; a real question beside a URL still does.
- Clicking a session Tab or its Pane body, including an already-focused Pane, acknowledges the indicated red/yellow event except for a current question. A direct window control acknowledges that exact window; a parent session Tab or Pane acknowledges its highest-priority actionable child. Touch taps and real terminal input use the same acknowledgement path for blockers and completion reminders. A question ASK stays visible through focus and draft typing and is acknowledged only when the next terminal prompt is submitted. Hover, automatic focus, scrolling, passive terminal reports, and merely leaving a Pane open do not acknowledge attention.
- Acknowledged red/yellow balls and their `ASK`/`BLK` labels immediately turn gray, fade once over the configured status pulse period, and disappear when that interval ends. Acknowledging a queued question leaves its still-working green ball intact. The same unchanged event stays hidden through refresh and reload; a new question, blocker, run, or reused process/pane identity gets its own lifecycle. Acknowledging a marker records that the user saw it and does not answer the question or dismiss the terminal application's prompt.
- Session status markers stay grouped immediately after the status circle and before the session title, and Tabber rows repeat the same status and repository badges shown on Pane Tabs: `BLK` for blocked, `ASK` for a current user question or approval request, including a queued Codex follow-up question, `TEST` while a test command is active, `OFF` while the terminal is disconnected, and `YO` when auto-approval is enabled or offered. Keep the group visible on narrow tabs and avoid repeating these labels after the title.
- Keep the `YO` status marker visible when the backend reports auto-approval enabled or offered. Add the toggle action only when the backend advertises `yolo.auto-approve.v1`; otherwise render the marker read-only. After a toggle, use the server response as the authoritative state and consume `auto_approve_changed` snapshots so other tabs converge without polling. A successful toggle updates the marker without leaving a global status message.
- With YO enabled, a current Codex `■ Selected model is at capacity. Please try a different model.` notice remains blocked and triggers recovery immediately, then every 10 seconds. An empty composer receives exact `continue` through bracketed paste followed by a real Enter key; pasted newlines and a text-plus-Enter typing burst cannot substitute for submission. An unsubmitted `continue` owned by the same worker/session/pane/process receives Enter only. Preserve user drafts. Revalidate the current notice, live agent status, identities, YO enablement, and dry-run before delivery; stop on resumed work, newer output, disabling YO, or a changed target. Key delivery and confirmed resumed work are separate outcomes. Dry-run records the intended recovery without terminal input.
- Push updates received before the next display frame preserve every dependent patch, file change, acknowledgement, and notification in order. Independent search scopes and index roots stay independent. Complete replacement snapshots may coalesce; a stalled display frame drains bounded pending work without losing transitions, and retired server epochs cannot update the page.
- Session-state transition logs use bounded event batches. A failed chunk leaves only its unacknowledged transitions queued; retrying it does not repeat transitions from successful chunks.
- Notifications identify their target without stealing focus. Repeated passive notices with the same displayed title and summary for one target reuse one visible card across producer keys and whitespace differences; after dismissal or expiry, repeats stay suppressed until 30 seconds have passed since the most recent occurrence. Repetition preserves the original countdown, Keep choice, and focused control. Different displayed messages remain separate. Successful terminal uploads open the numbered action chooser at the pane top-left and do not show a separate yellow Uploaded toast; upload errors and size-limit notices remain visible. Agent cards place the session and agent badges in a wrapping row above the message. The message uses the full card width with compact side padding.
- Pane and global toast notices stay below application menus, terminal popovers, and other menu choices so file-change warnings remain visible without blocking menu access. Global notices sit at the top-right inside the application content, 12px below the measured top pane headers and tab holders in regular and compact layouts. Header wrapping and layout changes update that clearance. Adding or removing a command notice keeps the same top anchor. The global stack scrolls within the visible application area on short screens; notices retain their full text and reachable Keep/Close controls. Shared notification cards use macOS-style rounded corners, soft shadows, dark readable text, and a solid yellow paper surface: warm post-it yellow in dark mode and a brighter yellow in light mode. Buttons and countdown accents keep enough contrast against the paper surface.
- Explicit indexing, removal, exclusion, already-indexed, rename, layout refusal, and pinned-cap announcements use the shared timed notification card with the configured countdown and close/keep controls. Initial and shared-settings index reconciliation stays silent. Routine footer and connection updates clear inherited overlay styling without generating notices; command progress, actionable failures, and authentication retain their own lifecycle.

- A newer YOmux version is announced while its pinned native executable and browser bundle are built in an owned staging workspace. Upgrade appears only after the build, version, and native launch checks succeed. A failed build keeps the version-available notice visible with the failure reason and no Upgrade action. Checking and recovery transitions update the same notice; reconnecting browsers read the current readiness. Newer status updates and later status requests retire earlier reads before those reads can change the notice or authorize confirmation. A change to a visible update notice replaces its previous content even when the new failure message appeared earlier; repeating an unchanged, manually dismissed notice stays suppressed. Clicking Upgrade rechecks readiness and confirms the selected target before activation. Checkout or installation changes reject activation with a visible error. Dry run performs preparation without installing or restarting.

- The Info Bar below pane tabs opens its session-details popover after the shared hover delay (1.3 seconds by default); leaving before the delay cancels opening.
