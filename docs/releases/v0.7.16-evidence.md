Landing record for annotated release `v0.7.16`. The candidate is branch `fix/v0716-git-view-loose-object-cache`, based on `v0.7.15^{commit}` at `feed729c9651112182b6161718b8156553ccdaec`. The final release commit is the object resolved by `v0.7.16^{commit}`; the exact pushed SHA is recorded in the release handoff after the tag and origin refs are verified.

## Shipped scope

- Blame and the Differ tab failed for the same reason. Before either could run its Git command, YOLOmux rebuilt a pinned view of every loose Git object. This repository has 4,981 loose objects, and one open and read over NFS costs about 2,382 microseconds. Rebuilding that view on every request took about 12 s, which exceeded the server's 10 s snapshot deadline and the browser's 5 s request deadline.
- The Git command was not the slow part. In a profiled 12.58 s Blame request, `git blame` took 0.11 s, or 0.8%, and building the pinned object view took 12.08 s, or 96.1%.
- The boot-local cache had 0 entries because it tried to hardlink objects from NFS into local `/tmp`. That always returned `EXDEV`, and the error was swallowed. YOLOmux now copies an object into the cache when it cannot link it. A loose object's name is the hash of its content, and Git publishes it by renaming a completed temporary file into place, so the copied object has the same content authority as a hardlink.
- Cache entries were keyed by source inode, which meant a cache lookup still had to open the source over NFS. They are now keyed by repository and object name. A repeat build reports 4,981 cache hits and 0 source reads.
- The cache previously took its cross-process lock and fsynced its accounting for every object. That produced 4,981 fsync calls and consumed 3.13 s of a 13.35 s cold build. One build now holds one cache session. If a build reaches its deadline, the entries it already published remain available to the retry.
- Cold loose-object reads now use a 16-worker pool. These reads wait on NFS latency rather than CPU, so overlapping them removes the wait without reading more data. The separate benchmark measured 7.00 s with 1 worker, 0.90 s with 8 workers, and 0.57 s with 16 workers.
- A fully cached build does not need that pool. Each layer now settles cached objects inline and starts workers only for objects that must be read from the repository. On the 5k-object store, avoiding an unused pool removes about 0.3 s of setup and host contention. A cold build took 2.05 s with 1 pool created; a warm build took 1.09 s with 0 pools, compared with 1.13 s when the pool was unconditional.
- Cancelling a test run could leave a temporary worktree-writer owner record behind and make the next run crash with `WorktreeWriterReleaseError`. The heartbeat writer removes that temporary on every normal exit, so it survives only when the process is killed after creation and before rename. Reclaim had already renamed the slot aside before it classified the temporary as foreign, leaving the directory orphaned. Reclaim now recognizes and removes an abandoned temporary created by its own owner-record writer, and still refuses any other entry. The module that creates the temporary now owns the name check too, so creation and reclaim use the same format.

The exact cancelled-run failure was:

```
INTERNALERROR> WorktreeWriterReleaseError: refusing to remove writer slot with unexpected entries: .owner.json.401950.140674180654784.1787679736965115809.tmp
```

- Opening a file no longer depends on Git history being available after the bytes have already been read. Open and its path validation return the file with a `git_enrichment` field naming why history is absent when Git exceeds its size or time budget. Enrichment has its own 2 s budget instead of inheriting the 10 s view-build deadline. A repository-changed refusal still stops the request, because degrading that case could serve one repository's contents as another's.
- The editor no longer turns every HTTP 413 into "File is too large to preview." A 21,549-byte `STATUS-REPORT.md` hit a Git budget under a 20 MB file limit and showed that wrong state, including the literal placeholders `{size}; limit is {limit}`. Open now treats only the file-size reason, or a refusal with no reason, as oversize. The too-large renderer also supplies the size and limit instead of letting an empty descriptor replace them.
- The debug panel now puts every `yolomux.py` web CPU line on the daemon chart with the other six services. The CPU chart keeps host binaries and the system total. The CPU family remains the single owner of each web PID and samples it at one cadence; the service-load family still has no `web` row, and the collector rejects any producer outside its six-service inventory.

## Known limits

The boot-local object cache is capped at 32,768 entries and 512 MB and does not evict entries. This repository uses 181 MB. Repositories on a network filesystem populate the cache with copies instead of hardlinks, so several large repositories can reach the cap. Once the cap is reached, publication stops and later builds return to reading those objects from the source.

The web CPU line reports a bucket average. The daemon chart's Avg/Max/Min control cannot change that line because the CPU family does not record a per-bucket range.
