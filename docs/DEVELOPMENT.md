# YOLOmux — Development

Conventions, architecture, build/test workflow, restart workflow, and API notes for contributors live here. End-user/operator docs live in [`README.md`](../README.md). AI-agent behavior rules live in [`AGENTS.md`](../AGENTS.md).

## Setup

Standard install via the Makefile (wraps `pip install -e .` + the static bundle build):

```bash
make setup        # pip install -e ".[yoagent]"  +  python3 tools/static_build.py
make dev          # same, plus the complete dev/test gate toolchain — see `make help`
```

`pyproject.toml` is the source of truth for Python deps and the floor (`requires-python = ">=3.10"`), so pip checks the Python version and resolves the runtime dependencies plus the `yoagent` / `dev` extras. `make setup` and `make dev` run the same Python-floor preflight before invoking pip. Use editable installs; this repository deliberately has no mirrored `requirements*.txt` files.

```bash
pip install -e ".[yoagent,dev]"      # deps + the `yolomux` command + agent SDKs + gate tooling
```

On externally managed system Python installs (PEP 668), create and activate a virtual environment first (`python3 -m venv .venv && . .venv/bin/activate`) instead of forcing `--break-system-packages`.

### Gate prerequisites

The `dev` extra is the complete Python gate dependency set: `mypy`, `pillow` (the Pillow import/package), `pytest`, `pytest-timeout`, `pytest-xdist`, and `selenium`. Install it through `make dev` or `pip install -e ".[yoagent,dev]"`; do not maintain a second hand-written requirements list. Browser lanes also require Chrome or Chromium and a compatible executable chromedriver. Selenium may discover a matching cached driver, but the gate performs no install or download. The xterm provenance check requires Node.js and npm, installs the versions pinned by `package.json`, and compares them byte-for-byte with `static/vendor/` through `make xterm`.

Linux full-gate hosts must provide at least 1,024 `fs.inotify.max_user_instances`, 65,536 `fs.inotify.max_queued_events`, 1,048,576 `fs.inotify.max_user_watches`, and 256 free inotify instances before heavy lanes start. `tools/check.py` reports a provisioning refusal rather than weakening or retrying the gate when those floors are unavailable. Managed startup runs the same shared capacity verdict and prints the current free-instance count or the full remediation warning; it remains advisory for normal startup because polling can still be correct. Raise only a deficient kernel maximum and verify the readback; do not lower a higher value. To persist the floor across reboot: `printf 'fs.inotify.max_user_instances=1024\nfs.inotify.max_user_watches=1048576\nfs.inotify.max_queued_events=65536\n' | sudo tee /etc/sysctl.d/60-yolomux-inotify.conf && sudo sysctl --system`.

For NFS-mounted source checkouts, source is the only gate path permitted on NFS. Put the virtual environment, `TMPDIR`, XDG config/cache/state/runtime roots, sockets, locks, browser profiles, logs, test evidence, and copied npm fixtures on a short host-local `/tmp` path. Set `PYTHONDONTWRITEBYTECODE=1` and `YOLOMUX_TEST_ROOT` to that short root; do not export a global `YOLOMUX_ROOT`, product directory overrides, or `PYTHONPYCACHEPREFIX` into pytest because the fixtures own their isolated product roots.

### Runtime-root durability

Sockets, live locks, service records, and background-owner records live below `RUNTIME_DIR`. YOLOmux prefers `XDG_RUNTIME_DIR`; without it, it uses the host temporary filesystem under `/tmp/yolomux-<uid>`. Operators running a long-lived server must ensure that path is not removed by `systemd-tmpfiles` while the server is live. Prefer setting `YOLOMUX_RUNTIME_DIR` to a private, local, mode-0700 runtime location with an explicit tmpfiles exclusion. The runtime root is scoped by readable host and boot prefixes; prior-boot siblings may be cleaned only when they are mode 0700, owned by the current user, and under the current host partition. A symlink, foreign owner, or unexpected mode is refused rather than adopted.

For an isolated server or test run, set only `YOLOMUX_ROOT=/short/private/path`. It derives YOLOmux-owned `config`, `state`, `cache`, and `runtime` below that path; startup removes ambient `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, `XDG_RUNTIME_DIR`, and `CODEX_HOME` from the rooted server environment so they cannot redirect writes. Codex credentials and configuration remain user-owned by default, so rooted Codex subprocesses receive `CODEX_HOME=~/.codex` and reuse the user's existing login without creating `<root>/codex`. An explicit `YOLOMUX_CODEX_HOME=<root>/codex` opts into an isolated Codex home for tests or other callers that require it; as with every `YOLOMUX_*_DIR` override, it must remain inside the root or startup fails. Choose a short root: startup enumerates the actual control and service socket names before creating directories and refuses a path that would exceed the portable Unix-socket limit. The ordinary root-unset defaults are unchanged.

Every explicit product path must be absolute, cannot be `/` or the home directory itself, and cannot resolve inside the shared checkout. This applies to `YOLOMUX_ROOT`, the config/state/cache/runtime/Codex overrides, `YOLOMUX_HOST_ARTIFACT_DIR`, `YOLOMUX_START_LOCK_DIR`, `YOLOMUX_LOG_DIR`, `YOLOMUX_CA_DIR`, `YOLOMUX_TOOL_LOCK_PATH`, `PYTHONPYCACHEPREFIX`, and `TMPDIR`; command-line log, TLS state, and CA output directories use the same resolver. In an unrooted run, `XDG_CACHE_HOME` and `XDG_RUNTIME_DIR` are base directories, so they must be absolute, cannot be `/`, and cannot point inside the checkout while YOLOmux derives a child below them. A relative `HOME` is also refused before startup can create a lock, stop a listener, or import product code. These checks reject unsafe inputs instead of resolving them against the process working directory.

## Project Conventions

### Version bump policy

Runtime `YOLOMUX_VERSION` lives in `yolomux_lib/infra/common.py`; the static package-version literal in `yolomux_lib/common.py` must always match it. Both are bumped only when publishing to `origin/main`. LOCAL `cps` / `yolo-cps` lands work on local `main` with no version bump and no push; ORIGIN / REMOTE `cps` rebases onto `origin/main`, increments the patch segment, folds both matching literals into the work commit, and includes `Version: 0.4.N` in the commit message body. The self-updater compares `YOLOMUX_VERSION` on `origin/main`, so SHA-only published commits do not cue update notifications, but local integration commits must not create fake versions. `tests/test_common.py::test_package_and_runtime_versions_match` rejects drift between the two required literals.

To find the latest committed version before ORIGIN publish: `git show origin/main:yolomux_lib/infra/common.py | grep YOLOMUX_VERSION` and add 1 to the patch segment, then apply that same version to `yolomux_lib/common.py`.

### Timing constants

JavaScript and CSS timing constants in `static_src/`, `static/yolomux.js`, and `static/yolomux.css` are split by purpose:

- UI / popup / display / animation timings use round whole numbers, for example `300`, `1000`, `1550`, `10000`, `20000`.
- Backend polling / refresh intervals SHOULD prefer slightly-staggered (often odd) values, for example `1257`, `3001`, `5003`, to spread client requests across ticks instead of piling up on the same one. This is a preference, not an invariant — several shipped defaults in `yolomux_lib/workspace/settings.py` are still round (`event_log_refresh_ms: 5000`, `server_event_poll_ms: 850`, `server_directory_event_poll_ms: 3000`); nudge them toward staggered values when you touch that area, but nothing enforces it today.

UI durations are perceived by users and read as deliberate at round values. When a request says "make it 1000ms", a UI duration keeps `1000`; a backend poll may use a nearby staggered value like `1003`.

Recurring browser work must register through `resetRuntimeInterval()`/`clearRuntimeInterval()`. The named recursive scheduler waits for an async callback to settle before starting the next full delay, so slow YO!stats, file-index, or debug work cannot overlap or degrade into back-to-back requests. Each live scheduler record exposes its source-of-truth class, last run, and whether the callback produced useful work or `no-change`; do not add direct application `setInterval()` loops or a parallel timer registry.

The source-level `runtimeIntervalCatalog` is the authoritative classification for every production `resetRuntimeInterval()` owner. The shared taxonomy distinguishes `poll:no-change`, `sample`, `lease`, `external-reconcile`, `repair`, `fallback`, and `local-display`. `latency` is the sole browser health sample; it also supplies the bounded YO!stats client-health observation, so `debug-client-health` is retired. `chat-relative-times` is local display only; `events-fallback`, `auto-approve`, `debug-stats`, `file-index-building`, and Tabber activity are fallbacks; `file-index-refresh`, `debug-system`, and `debug-logs` remain visible-surface `poll:no-change` reconciliation until their owners publish revisions. A healthy EventSource suppresses normal discovery reads; disconnect, visibility recovery, a missed revision, or a terminal stream failure permits one bounded, keyed repair rather than `refreshAll()`. Browser-to-server stats-observations upload, background/typing leases, the one-second host sampler, SSE heartbeats, native-watch safety scans, and external PR/update checks are not browser runtime-interval entries; they retain their respective source owners. Do not remove a catalogued interval merely because SSE exists: remove it only when the named owner publishes an equivalent revision and a focused regression proves the fallback/repair behavior remains correct.

Three server cadences are deliberately always on: background-owner's 1 Hz heartbeat makes failover prompt despite two small state writes per second; the CPU family samples and publishes at 1 Hz to preserve continuous history; and the stats lease renews at 1 Hz to keep sole-writer ownership intact. Change any of those cadences only with an operator decision, not as a browser-idle optimization.

### Responsive UI sizing

Do not hard-code layout capacity around one browser window, OS, zoom level, or font rendering. For menus, panes, dropdowns, tab lists, and editor/viewer surfaces, prefer intrinsic sizing, flex/grid allocation, percentages, viewport units, and shared CSS variables over fixed pixel width buckets. Fixed pixels are acceptable for hairlines, icon glyphs, and the base spacing-token definitions, but component gaps, padding, and margins from 1–12 px must consume `--space-1` through `--space-12`; negative token spacing uses `calc(-1 * var(--space-N))`, never invalid `-var(...)`. If JavaScript must set a size, derive it from measured DOM content and clamp it to the current viewport/container.

## Source Layout

### Runtime And Layout Names

Use explicit names whenever runtime tmux metadata and browser layout appear together: `TmuxSession`, `TmuxWindow`, and `TmuxPane` describe tmux objects; `YOPane` and `YOTab` describe the browser layout. `TmuxPaneInfo` is the backend record for a `TmuxPane`; do not introduce a new unqualified `PaneInfo` use, because it is ambiguous with `YOPane`.

The main server entry point is `yolomux.py`, which delegates to `yolomux_lib/cli.py`. Request routing lives in `yolomux_lib/server.py`, application coordination lives in `yolomux_lib/app.py`, local Unix RPC framing/lifecycle lives in `yolomux_lib/local_services/`, visible Claude/Codex tmux pane control lives in `yolomux_lib/tmux/agent_tui.py`, shared Claude/Codex structured communication lives in `yolomux_lib/agent_comms/` (Codex app-server, Claude stream-json, and normalized stream events), and shared helpers live in smaller modules such as `metadata.py`, `sessions.py`, `session_files.py`, `transcripts.py`, `uploads.py`, `events.py`, `websocket.py`, `approvals.py` (the approval-prompt detection pipeline), `runtime_env.py` (one dependency-light PATH healer used by both the server and Codex child environment), `atomic_file.py` (cross-process file lock + atomic write), `cache.py` (the shared `TtlCache`), and `activity.py` (the per-session/window user+agent activity ledger). The current statsd service entry point is `stats_current/service.py`; it owns the sole YO!stats SQLite writer, asynchronous four-layer materializer, and exact snapshot/delta cache. Other local service entry points are `search_indexer.py` for `indexd` Quick Open SQLite ownership, `batchd.py` for bounded stateless CPU tasks, and `approvald.py` for target-keyed YO auto-approval workers. `batchd` owns its one-worker lane slots, their generation fence, and the daemon-wide two-predecessor quarantine budget; non-batchd shutdown and service lifecycle remain separate owners. The elected `app.py` process owns independent YO!stats collection workers and talks to services through `StatsCurrentClient`, `SearchIndexerClient`, `BatchClient`, and `ApprovalClient` rather than importing service internals. In the current-only architecture, web processes never open or aggregate the stats database; they forward current binary RPC snapshots produced by statsd. Recursive tree discovery is never request-path/API-process work: indexed-repository discovery is a maintenance-priority `batchd` task, and `app.py` serves the last completed snapshot while a refresh is pending.

### `TmuxWebtermApp` extraction direction

`TmuxWebtermApp` remains the HTTP/tmux compatibility facade. Four composed owners now provide the accepted extension seams: `WatchBridge` owns client demand, watch/status-generation workers, event publication, and their teardown; `SessionFilesCoordinator` owns session-files cache, work, and publication state; `ActivityCache` owns transcript/activity cache and refresh state; and `SystemStatusProjector` owns retained backend-health inputs and immutable system-status projection. Extend the existing owner when behavior belongs to it. For a genuinely new domain, move its state record, locks, worker lifecycle, and behavior together into one composed owner, inject named callbacks, and keep explicit app forwarding signatures until consumers migrate.

Do not split by method prefix, create an app-shaped service, use mixins or a generic service locator, or leave a compatibility field as a second mutable owner. Characterize payload bytes and callback/lock/side-effect order before the move; cover start, replacement, stale completion, failure, stop, and shutdown; then negative-search the retired facade state.

### Terminal Wheel Routing

`routeTerminalScrollLines()` chooses alternate-screen app input from the live tmux `alternate_on` signal, then checks xterm mouse tracking; it never identifies an application by name. Every discrete wheel notch must deliver at least one line on every destination: tmux scrollback, local terminal scrollback, and `forwardAltScreenWheel()`. A pixel-delta physical wheel is identified by its legacy `wheelDelta` field and must not wait for fractional accumulation; continuous trackpad deltas do accumulate in `altScreenWheelRemainder` so smooth scrolling remains smooth. The alternate-screen sequence is clamped by `terminalWheelMaxLinesPerEvent`, and the remainder is cleared when the route leaves alternate screen or its session detaches.

Detached pane pop-outs are owned by `static_src/js/yolomux/90_pane_popout.js` and the `/pane-popout` placeholder route. Add support through `TAB_TYPES.canPopout`, `openPopout`, or `popoutRenderer`; do not create per-pane popout registries or document writers. Phase-1 popouts are rendered snapshots, so live terminal/transcript and interactive command panes must remain disabled with an explicit `popoutDisabledReason` until they have a live bridge design.

### Central State Containers

`agentWindowActivityRecords` owns per-agent-window transition state; `sessionStatusRecords` owns per-session status and notification state; `toastRecords` owns toast nodes/timers; `dragState` owns one active drag; `paneViewState` owns durable pane scroll; `layoutUrlState` owns URL application; `clientEventTransportState` owns the browser SSE lifecycle; `fileExplorerDirectoryRecords` owns directory-observation signatures; `fileExplorerFsResourceRecords` owns filesystem resource cache records; `StatsCurrentRuntime` owns the elected app's independent per-family collection scheduler threads, locks, wake events, diagnostics, and source caches, while statsd alone owns durable original observations, usage atoms, family folds, immutable materialization generations, pre-encoded snapshots, and exact deltas; `SessionFilesService`, `ActivityTranscriptService`, and `ClientWatchService` own their server locks/cache/work/watcher records; and `approvald` owns target-keyed auto-approve workers. Readers use their named selectors/helpers and lifecycle owners; consumer-local mirrors of the same keyed fact are forbidden.

For every refactor or new UI behavior, record `Existing parent checked: <symbol>` or `New shared parent: <symbol and reason>` plus the exact searches used. A DONE note or handoff also records the negative search proving retired copies are gone and the net non-generated line change.

The approval-prompt detection pipeline lives in `yolomux_lib/approval/approvals.py` (one shared owner: `app.py`'s read-path, the `AutoApproveWorker` act-path in `yolomux_lib/approval/auto_approve_worker.py`, and the standalone `tools/auto_approve_tmux.py` CLI all call it; the CLI re-exports it). `agent_tui.py` is the public owner for combining that pure detector state with tmux captures, cursor facts, composer draft/ghost state, transcript activity upgrades, clear, paste-submit, and submit verification. An enabled session may have one worker per detected agent-pane target; `approvald` is the single target-keyed owner of each worker, its target flock, and its session association.

## Normalized Session Work Metadata

`yolomux_lib.metadata.session_work_graph()` is the only backend owner of repository/work metadata. It serializes `work_graph.version`, a monotonic `generation`, and canonical maps for `tmux_sessions`, `tmux_windows`, `tmux_panes`, `runtime_actors`, `path_observations`, `git_worktrees`, `local_repositories`, `hosted_repositories`, `local_branches`, `pull_requests`, `linear_issues`, and `worktree_branch_activity`. The graph uses snake_case API fields; browser selectors use camelCase rendering projections only after reading the graph.

`PathObservation` links tmux/actor evidence to at most one nearest `GitWorktree`. A `GitWorktree` belongs to exactly one `LocalGitRepository`, identified by Git common-dir, so primary and linked worktrees share one local branch inventory without duplicating it. Separate clones retain separate LocalGitRepository records even when they map to one HostedRepository; PullRequests belong to the HostedRepository and associate to zero or more LocalBranches. Graph validation runs before serialization and rejects dangling IDs.

`session_to_json()` emits one authoritative `work_graph` plus non-Git `window_metadata` cwd rows. New consumers must use the graph-aware shared frontend selectors (`sessionWorkSummary`, `focusedRepositoryIdsForTmuxTarget`, `branchIdsForGitWorktree`, and `pullRequestIdsForTmuxTarget`); neither `session.project` nor `window_metadata[].git` exists in the API. A schema-valid graph, including an empty one, is authoritative. Metadata refreshes use the graph generation to reject stale results rather than wall-clock ordering.

## Static Build

After changing any frontend source file, rebuild the served single-file assets:

```bash
python3 tools/static_build.py
```

Run with `--check` before committing to verify generated assets match source:

```bash
python3 tools/static_build.py --check
```

The tracked pre-commit hook also runs that check against the staged index whenever `static_src/` is staged, so a source-only commit cannot ship a stale bundle. Enable it once in every fresh clone with `git config core.hooksPath .githooks`; linked worktrees that share the clone's Git directory inherit that setting.

### Exclusive latency certification

`python3 tools/check.py` ends with one exclusive latency-certification phase. The parallel functional lanes run first, `pytest-gate-serial` then runs its correctness/timing nodes alone, and the phase joins everything the gate owns, qualifies the host, runs one serial pytest invocation naming exactly the certification node ids, and qualifies the host again. Retirement means three measured things, not a sleep: zero surviving descendants of the runner, zero live containers built from this checkout's test image, and one `os.sync()` so the writeback the lanes caused is finished by the gate rather than observed by the qualifier as ambient disk load. The container check is not optional - pytest re-executes itself inside the test image, so the lanes' real work is a child of the container runtime and a process-tree walk alone reports "retired" while a full browser suite is still winding down. A deadline breach at 30 seconds is a refusal naming the surviving pid, command line and container id. Nothing else runs during it. A focused `--lane` selection is deliberately not a certification and says so instead of exiting 0 as if it had certified; `--certification-only` runs the phase alone. The phase runs even when a lane already failed, because a phase that only executes on an otherwise green gate would never be observed on a box where some lane is usually red.

`tests/latency_calibration.py` is the one owner of qualification, the declared reference envelopes, and the fixed-ceiling verdict; `tools/check.py` and every certification unit read that module so a threshold cannot drift between the gate and the test it admits. Host qualification asserts `procs_running` p75, CPU/IO/memory PSI stall fractions computed as deltas across the probe's own window, whole-device disk busy fraction and in-flight depth from `/proc/diskstats`, one fixed integer CPU work unit, and one fixed warm-cache SQLite storage work unit on the filesystem the units use. A qualified first window is admitted immediately; after a red live window, the owner measures at most five total windows and recovers only after two consecutive qualified windows. That bounded convergence covers the measured post-gate red/green/red scheduler sequence while sustained or alternating load still refuses. This changes neither thresholds nor product timing ceilings, adds no fixed sleep, and retains all measured windows in evidence; explicit injected measurements stay single-shot so negative controls never retry fixed evidence. The 1/5/15-minute load averages and the PSI `avg10`/`avg60`/`avg300` fields are recorded as evidence and never asserted: they are decaying estimators of a state that has already ended, so immediately after the parallel lanes retire they still report the retired load. A signal the kernel does not expose is an unqualified host, not a silent pass. `HOST_QUALIFICATION_REFERENCE_CONDITIONS` records the measured baseline and gate-loaded populations each limit sits between, including the two signals that did not separate them.

A ceiling is a product budget and is never scaled by a host. The retired `latency_budget_result` multiplied every ceiling by a 1x-6x calibration factor, which let a slower machine authorise a slower product; `fixed_ceiling_verdict` replaces it and takes no host input at all. Calibration decides only whether, and which statistic, may be certified: an unqualified host produces `NOT CERTIFIABLE` with its raw evidence, never a skip and never a widened budget. The browser probe carries two thresholds on one measurement. `CALIBRATION_ADMISSION_MS` (25.0 ms) is the admission envelope beyond which no verdict may be reached; `CALIBRATION_REFERENCE_MS` (16.7 ms) is the stricter selector a unit may use to decide which statistic it certifies, and they may never invert. 16.7 ms is one vsync frame, not a CPU speed: the probe crosses a `requestAnimationFrame` boundary, so that value says the fixed work unit fitted inside a single frame. Using it as an admission gate refused five of nine otherwise-qualified exclusive-phase runs whose measured latency was far inside the product ceiling, so admission is set at 1.5 frames, above every one of 63 measured quiet samples (15.4-19.4 ms) and below a host that loses a whole extra frame. The certified budgets are S1 keystroke wall latency 3.0 ms (nearest-rank p99 of 120 samples per round, quiet and pressured, one browser and one page load), chat-store operations 250 ms each over 30 samples, I3a drag preview 150 ms, I3b Dockview full load 100 ms, and cold 24-hour stats HTTP requests 50 ms each. Each unit has a sibling in the parallel lane that asserts only counts, identities and completeness, because those are insensitive to renderer or disk scheduling; the stats sibling also retains real injected-delay negative controls for every routed endpoint.

`docker/run-tests.sh` holds one `FORWARDED_TEST_ENV` allowlist. pytest re-executes itself inside the test container, and `docker run` passes through only the names in that list, so an admission variable missing from it does not fail loudly: the node is silently skipped and the run still reports green. Any new admission flag must be added to the allowlist in the same change that introduces it. The control that proves the forwarding works is the same node id run twice with only the allowlist differing.

Exit codes are `0` certified, `1` a lane or a certification unit failed, `2` usage, `3` another expensive check or worktree writer owns the checkout, `4` `NOT CERTIFIABLE`, `130` interrupted. The refusal precedence is deliberate and strongest first: owned processes did not retire, host unqualified at preflight, host unqualified at postflight, a named unit did not run, then a unit breached its ceiling. A postflight refusal outranks a unit failure because a breach measured on a host that was not qualified is not evidence about the product; it is reported as `NOT CERTIFIABLE` with the unit evidence attached rather than blamed on the code. Every outcome carries a machine-readable reason and lands in the run report under `certification`, alongside the raw artifacts in the phase evidence directory under `/tmp`.

Host fitness has exactly one owner and every certification unit consults it. `latency_calibration.certification_phase_fixture(env_name)` builds each module's `certification_phase_only`, which makes both decisions before the unit's own browser or server fixtures load the machine they describe: not asked for is a `pytest.skip` the runner reports as `certification_unit_did_not_run`, and an unqualified host is `NOT CERTIFIABLE` with its raw evidence. It returns the host qualification, so each unit merges it with whatever else it qualifies on and carries the whole measurement in its artifact. `certify_verdicts` owns the three outcomes a unit may have - refusal, breach, certified - and `assert_fixed_ceiling` is its single-verdict spelling. A unit that refuses is classified `certification_unit_not_certifiable`, ahead of a breach, for the same reason a postflight refusal is: the units qualify at the moment they run, which the preflight taken before the whole serial run cannot.

That consolidation deleted three divergent copies. `tests/test_gate_tmux.py` had a private `_certification_phase_requested`, a private `certification_phase_only` fixture and a private `_certification_verdict`; `tests/test_gate_interaction.py` had a second copy of the fixture; `tests/test_chat_store.py` had a `CHAT_STORE_CERTIFICATION_MAX_LOAD_PER_CORE` precondition on `os.getloadavg()[0]`, exactly the decaying estimator host qualification refuses to assert on. That estimator failed 2 of 6 full gate runs at `load_average_1m` 17.31 and 17.52 against its own 16.0 limit while the phase's own windowed preflight had qualified the same host. Measured directly on keivenc-linux1: 20 s after 40 spinners exited, the 1-minute average still read 35.34 and vetoed, while the windowed owner measured `procs_running` p75 7 and cpu some-stall 0.0074 and correctly qualified; at 0 s and 5 s after the load both refused, so the estimator was never right where the windowed owner was wrong. `tests/test_check_runner.py` pins the consolidation by AST: no certification unit may call `getloadavg`, define a private admission helper, or declare a private host threshold, and every node must take `certification_phase_only` as its first parameter from the shared factory.

The phase carries its own negative control, `test_certification_host_qualifier_refuses_a_genuinely_loaded_host`, as the last certification node. It uses the fixture's own qualified baseline, puts real CPU and fsync load on the same box, and requires the same thresholds to refuse it while naming a signal that load actually moved - so ambient load cannot satisfy it. With its load generator neutered it fails, which is what makes it a control rather than a decoration.

## YO!stats stability contracts

Three standing rules exist because each was violated by a real incident (2026-07-14/15):

1. **One exact request and policy owner.** `yolomux_lib/stats_current/resolution.py` owns the `{1,10,60,300}` universe, Range matrix, AUTO choice, 600-bucket bound, and live cadence. The current browser path builds one `GET /api/stats-snapshot` request from server capabilities, and statsd returns that exact key or a structured error; no hand-rolled range table, hidden point limit, alternate reader dialect, or silent resolution substitution is allowed.

2. **Family manifest, no cross-family flags.** Per-family facts, native cadences, storage fields, fold rules, wire groups, and chart mapping live in one generated/shared family manifest. One family's inclusion or optimization flag cannot strip another family's data. Agent/Model token dimensions and YO!cost derive from the same identity-deduplicated usage atoms and must reconcile.

3. **Stats schema/protocol skew fails closed before mutation and coexists by scoped identity.** Every writer reads database application/schema/minimum-writer markers without mutation. Each compatible build uses `stats-v<schema>.sqlite3` and `statsd.p<protocol>s<schema>.sock`, so mixed worktrees never share a writer daemon or database. A stale page writer treats 426 as terminal; a current read client clears its local fence and retries only its own scoped service, never another build's daemon.

Contract suites exercise each current pipeline layer: real original-observation store, asynchronous four-layer materializer, statsd cache, HTTP forwarder, and render-only browser matrix, while separate RPC and route tests pin the binary transport and HTTP dispatch boundaries. Coverage includes every allowed Range x AUTO/explicit resolution, all families, exact deltas and cadence, migration/rollback/deletion, old-writer immutability, no-data, fair all-client browser aggregation, and cache-hit zero-DB/zero-aggregation behavior. The final cutover proof still runs the complete stack through a real socket and HTTP listener; old request/wire goldens are deleted rather than pinned behind a flag.

### Current-only storage and migration

The current schema-versioned stats database stores only original observations, identity-deduplicated usage atoms, covered epochs, explicit unavailable spans, migration reconciliation, and schema metadata. Explicit unavailable spans are coverage facts for known outages or migrated aggregates that cannot be reconstructed; they cannot overlap covered epochs. Writer fences preserve compatible migration repairs and startup diagnostics; older writers stop before mutation. Exact coverage overlapping an unavailable span is not repairable without guessing, so startup fails closed and preserves the database. Derived `1s/10s/60s/300s` display layers are immutable statsd memory, rebuilt asynchronously from a consistent snapshot and updated through the same deterministic dirty-cell fold; web requests never open SQLite or run a fold. [`docs/specs/STATS_API.md`](specs/STATS_API.md) owns the current schema, writer protocol/build, filename, and socket details.

Every process capable of writing first reads `application_id`, `user_version`, schema generation, minimum writer protocol, and minimum writer build through a read-only preflight. A newer schema or minimum writer produces terminal `SchemaTooNewError`/`upgrade_required` before mutation and stops spawn, replacement, and retry behavior while preserving the database/WAL/SHM bytes and metadata. Writer build 3 fences the fail-open legacy migration and startup diagnostics. Background-owner records advertise their stats writer build; when an older preferred owner cannot pass the active fence, the compatible newer generation inherits its priority through the existing release/takeover path and keeps the sole sampler alive. The versioned filename is not exposed through an alias or symlink to retired `stats-history.sqlite3`, so an old runner can recreate only its retired-path database; current startup never imports that file into serving and removes it through idempotent retirement cleanup. A genuinely corrupt database is preserved as a forensic sidecar; a merely newer database is never treated as corrupt. Transcript usage collection is incremental and reset-safe: one steady-state global pass reads at most 4 MiB or 4096 complete records across deduplicated Claude/Codex transcript families, persists offsets only through complete lines, rereads zero bytes for unchanged files, and resumes cold backfill on later native-cadence passes without blocking other collectors. Claude discovery uses the shared per-directory catalog and the same bounded reverse-name plus newest-mtime candidate selector as Codex, but only top-level project JSONL files seed independent session families; each root then expands through its own `subagents/` tree. A pane-owned root keeps its tmux key, while an unowned sibling gets a bounded stable project/session agent key and newest-mtime cold priority. The protocol-24 orphan-fork repair is a one-time asynchronous exception capped at 8 MiB or 8192 records per pass so tombstone receipts acknowledge and persist promptly on the target Mac; it records exact copied-prefix tombstones only through the explicit handoff, commits a versioned completion marker, and then uses the steady-state ceiling permanently.

The atomic all-source migration quiesces collectors and the sole writer, consumes every supported old table/journal/token/usage source, preserves the finest recoverable originals, converts unreconstructable coarse-only spans to explicit current no-data, recalculates all four layers, reconciles family counts/coverage/epochs/tokens/costs, then activates the new marker/fence. Success deletes old tables, files, sidecars, import markers, request dialects, response shapes, and runtime fallbacks; failure leaves the current database unactivated and the migration retryable. There is no dual-format aging period.

The atomic migration vacuums its shadow database, verifies zero freelist pages plus `integrity_check`, and activates that compact file only after reconciliation succeeds. At runtime, statsd is the one retention and compaction owner: one-minute cutoff sweeps keep original rows within the 48-hour `RETENTION_SECONDS` policy, the configured local time still owns the daily maintenance occurrence, and the existing quiet-gated hourly VACUUM reclaims free pages with a one-hour maximum defer. Writer connections explicitly use a 1000-page automatic checkpoint and an 8 MiB retained WAL allocation limit; a successful VACUUM truncates its rewrite-sized WAL before and after persisting the completion marker, because a passive checkpoint recycles logical frames without shrinking the file.

## Login rate limiting

`yolomux_lib/login_rate_limit.py` is the one owner of login throttling; both password paths (`AuthMixin.handle_login_submit` and the Basic-auth branch of `require_auth`) route through `AuthMixin.verify_login_credentials`, which checks admission BEFORE the PBKDF2 verifier and records the outcome after. Design rules to preserve:

1. **Gate before the hash, one shared owner.** Admission is an atomic `BEGIN IMMEDIATE` check-and-reserve in a single WAL SQLite file under `STATE_DIR`, shared by every port. It runs before `auth_identity_for_credentials`, so a blocked attempt costs no password hash and cannot be used to burn hash CPU. Never add a second ad-hoc limiter map in `server_auth.py`; `ChatRateLimiter` is in-process/fixed-window and intentionally NOT reused here.

2. **Two O(1) primitives, chosen deliberately.** Token buckets for four hierarchical network scopes (exact, /24·/64, /16·/48, global) and a staged-backoff counter for the username scope. Token bucket was picked over fixed-window (boundary burst), sliding-window-log (O(N) state under a distributed attack — measured 2000 distinct-IP attempts collapse to ~400 rows via the coarse buckets), GCRA (equivalent, less legible), and an ASN/reputation DB (external-dependency cost). Network buckets charge every admitted attempt including successes; the username counter advances only on a completed failed verification and resets on success (NIST). A request blocked at admission must never advance the username counter or extend its cooldown.

3. **No information leak, fail closed.** Rows are keyed by HMAC(scope‖key) under a 0600 secret, so raw usernames/IPs are never stored. The 429 body/status/timing is identical for known and unknown usernames and reveals neither the firing scope, attempt counts, nor a precise `Retry-After` — only a coarse minutes/hours band. A store failure fails closed (generic bounded response), surfaced as `login_throttle.healthy=false` in the admin System report. Setup mode and `YOLOMUX_TEST_AUTH_BYPASS` short-circuit before the limiter; valid cookie authentication does not run the password verifier and is never throttled.

4. **Client IP = socket peer only.** `X-Forwarded-For`/`Forwarded` are never trusted. Escalation (`yolomux_lib/login_escalation.py`: decoy challenge, expiring firewall/proxy DROP) is defense-in-depth, OFF by default: edge rules build argv (never a shell string), carry a TTL and cap, exclude trusted CIDRs, and fire only for volumetric network scopes — never a username lock. Policy overrides load from a validated `CONFIG_DIR/login-rate-limit.json` (not `auth.yaml`, whose users-only parser would drop the section on its normalization rewrite); malformed/incoherent overrides fall back to the safe defaults.

The mechanical WAL open/migrate primitives (`open_wal_database`, `enable_wal_with_retry`, `begin_wal_migration`, `load_or_create_secret_key`) live in `atomic_file.py` and are shared with `ChatStore`/`ChatCursorCodec` rather than copy-pasted. Coverage: `tests/test_login_rate_limit.py` (fake-clock bucket/backoff/threat/persistence/concurrency), `tests/test_login_throttle_integration.py` (both HTTP paths, bypass/setup preservation, no-hash-on-block, edge trigger), and `tests/test_login_escalation.py` (decoy + edge controller, all mock-runner).

Browser fixtures are served over a throwaway localhost HTTP origin, not `file://`. Chrome 150+ blocks a `file://` document from loading `file://` subresources in an unrelated directory, so a fixture in a temp dir can no longer pull the `REPO_ROOT/static/*` bundle/vendor/font assets. `browser_layout.py` lazily starts one `ThreadingTCPServer` rooted at `REPO_ROOT`; reference repo assets with `fixture_asset_url("static", ...)` and write/serve a fixture page with `serve_repo_fixture_page()` + `fixture_page_url()` (never `page.as_uri()` for a page that loads the bundle or any repo asset). The single shared origin means: the handler sends `Cache-Control: no-store` (http caches by URL — a same-name overwrite would otherwise serve the stale page); each page load gets a unique URL so Chrome's back/forward cache cannot restore a prior test's live JS state; and `_reset_browser_state()` clears all origin storage between tests (per-file `file://` pages used to get opaque-origin isolation for free). Self-contained inline fixtures with no external assets may still use `file://`. If Chrome auto-updates and the lane breaks again, check the console for `net::ERR_ACCESS_DENIED` / mixed-origin `NetworkError` before assuming a product regression.

Every full-bundle browser fixture goes through `load_live_runtime_boot_fixture()`, which owns bundle readiness; the raw `_live_runtime_boot_fixture_html()` builder is private to that helper module. ### Restart workflow

After every YOLOmux change in a dev worktree, restart that active dev server and verify it before reporting the change ready for testing. Restart prod only when explicitly requested.

Use `boot.sh` from the checkout you want to serve. `boot.sh` and `yolo-dev-start` share one process-lifetime startup lock from `tools/startup_common.sh`, so a second launcher fails before it stops or starts any server. They also share a slow-ramp load gate: before each agent or server mutation, one- and five-minute load must be below the CPU budget, capped at 8 CPUs on macOS even when the OS reports more logical CPUs. The launcher waits up to `YOLOMUX_START_LOAD_WAIT_SECONDS` (300 seconds by default) and stops the ramp rather than adding another process under sustained load. When an operator has measured a known persistent host service separately, `YOLOMUX_START_LOAD_DISCOUNT_CORES` may discount that many busy cores from both load checks; the value must be finite and non-negative, is capped at the scheduling CPU budget, and the launcher reports raw load, effective load, and the applied discount. This explicit adjustment does not bypass the shared lock, per-port lease, listener stability, or ownership checks. `boot.sh` also serializes each port, restarts only that listener, waits for the old listener to leave the port before launching the replacement, sets `PATH` explicitly before launch so agent CLIs under `~/.local/bin` are visible, defaults `MALLOC_ARENA_MAX` to 2 so threaded JSON/transcript work cannot retain one glibc arena per request thread, and appends logs under `/tmp` by default. The server holds a process-lifetime per-port lease, so direct launch and self-update races fail before app/background initialization. On Linux the script finds listeners with `ss` and uses the supported `setsid`/nohup detacher. On macOS it finds listeners with `lsof` and supervises web processes in per-port sessions on the private `yolomux-services` tmux socket; this keeps them out of the user's tmux roster while preserving the caller's Files and Folders access to checkouts under `~/Documents`. A legacy transient `local.yolomux.<port>` launchd job is removed during restart because launchd's daemon context can receive `EPERM` when serving those files.

```bash
./boot.sh
```

The script accepts any valid TCP port. It defaults to HTTPS `8880` on macOS and `7770` on Linux and still passes the compatible `--self-signed` spelling plus `--dang`; the CLI itself now defaults to the same self-signed HTTPS behavior. `YOLOMUX_PORT` selects an arbitrary primary port and keeps the normal non-dev launch behavior. The standard Linux fleet uses `7771` through `7773` for dev worktrees, and Linux autossh exposes `ereview:7770-7773` directly. The standard macOS fleet uses `8881` through `8883` for dev worktrees, and Mac autossh exposes `ereview:8880-8883` directly; there is no Linux-to-Mac forwarding hop and no standard `8000-8003` fleet. For a dev worktree, run the script from that checkout and pass the port you chose; non-primary ports use `--dev` automatically:

```bash
(cd ~/path/to/dev-checkout && ./boot.sh <dev-port>)
```

Override with `YOLOMUX_PORT`, `YOLOMUX_HOST`, `YOLOMUX_LOG_DIR`, `YOLOMUX_START_LOAD_WAIT_SECONDS`, `--port`, `--dev`, or `--no-dev` when testing a non-standard instance. `YOLOMUX_BACKGROUND_OWNER_PRIMARY_PORT` pins background ownership to one preferred server while retaining automatic follower failover; `boot.sh` defaults it to its selected primary port. Use `./boot.sh --print-command <dev-port>` to inspect the launch command without restarting anything.

For the standard multi-worktree stack, `yolo-dev-start` defaults the preferred server to `8882` on macOS when the second dev worktree exists (`8880` otherwise), and to `7770` on Linux. Override it with `YOLOMUX_PRIMARY_PORT`. The preferred server starts first; each port must then pass readiness, exactly-one-process, three-sample ownership, empty-refresh-queue, and system-load gates before the next port starts. Discovery checks use the read-only `/api/tmux-session-exists` roster endpoint and must never force a full transcript/metadata rebuild. Every checkout must advertise the same `BACKGROUND_OWNER_PROTOCOL_VERSION`; a stale worktree causes a preflight refusal before tmux, the private macOS service supervisor, listeners, or ownership are changed.

To restart a dev worktree in no-auth test mode:

```bash
YOLOMUX_TEST_AUTH_BYPASS=1 ./boot.sh <dev-port>
```

Four footguns: (1) never `pkill -f` broad YOLOmux patterns; kill only the listener for the selected port; (2) run `boot.sh` from the checkout you intend to serve so a dev port does not accidentally serve another worktree; (3) never bypass the shared startup lock or replace the read-only roster check with `/api/transcripts?force=1`; (4) a backend `.py` change only takes effect after the Python process restarts, because `static_build.py` does not touch backend code. If a restarted server appears ready and then disappears, check whether readiness was served by the old listener; `boot.sh` must fail instead of launching over a still-bound old PID. The in-app self-update path likewise treats a failed, timed-out, or unlaunchable `tools/static_build.py` run as blocked and must not restart into stale generated assets; periodic update-check exceptions are logged rather than hidden.

Verify after restart:

```bash
ps -ef | grep "yolomux\.py.*<port>" | grep -v grep
ss -tlnp 2>/dev/null | grep ":<port> "
curl -sk -o /dev/null -w "ping: %{http_code} %{time_total}s\n" https://localhost:<port>/api/ping
curl -skL -u <user>:<pass> https://localhost:<port>/ | grep -oE 'YOLOmux [0-9.]+' | head -1
```

Expected: one `yolomux.py` process, `LISTEN` on the intended port, `ping: 401` in under roughly 100ms, and the rendered version matches `YOLOMUX_VERSION`. If verification fails, inspect the appended `/tmp/yolomux-<port>.log` log for the previous launch error and the latest `boot.sh launching port ...` marker.

If you intentionally started with `YOLOMUX_TEST_AUTH_BYPASS=1`, `/api/ping` and `/api/settings` should return `200` without cookies. If a normal login-gated server returns `200` for those unauthenticated routes, auth is accidentally bypassed.

## Production Sync (`cps`)

`cps` (the `yolo-cps` skill) has two modes, chosen by the trigger word:

- **LOCAL (default — "cps" / "yolo-cps" with no qualifier):** rebase the dev branch onto LOCAL `main` and land it on local `main`. NO version bump, NO push.
- **ORIGIN ("cps origin" / "cps remote"):** rebase onto `origin/main`, bump the version, land on local `main`, then push to `origin/main`.

Edits happen in a dev checkout; the integration/production checkout (which holds `main`) is read-only during sync and shares the same `origin`. Because `main` is checked out in the production checkout, you cannot check it out in a dev worktree — land work by committing on the dev branch, rebasing it onto `main` / `origin/main`, then fast-forwarding `main` from the production checkout.

ORIGIN-mode sequence from the dev checkout:

```bash
python3 tools/check.py                       # the full gate (see Tests above)
git fetch origin && git rebase origin/main   # rebase onto the published tip
# bump matching YOLOMUX_VERSION literals in yolomux_lib/infra/common.py and yolomux_lib/common.py, folded into the work commit
git add -- <explicit-files>
git commit -m "<message including Version: 0.4.N>"
git -C <production-checkout> merge --ff-only <branch>    # land on local main — its OWN exit-checked command
git -C <production-checkout> push origin main            # only after the ff-merge succeeds
```

LOCAL mode is the same minus the version bump and the final `push` (stop after the ff-merge).

Rules:

- ORIGIN mode MUST bump matching `YOLOMUX_VERSION` literals in `yolomux_lib/infra/common.py` and `yolomux_lib/common.py` in the same commit; the auto-updater checks the runtime value on `origin/main`, not the commit SHA, so SHA-only commits do not cue the update. LOCAL mode does NOT bump.
- Never use `git add -A`; screenshots and scratch files must not get swept in.
- The `merge --ff-only` into the production checkout MUST be its own exit-checked command — NOT piped through `tail`/`grep` and NOT `&&`-chained straight into the push. A pipe's exit status is the last stage's, so a DIVERGED ff-merge fails silently and a chained `push origin main` then publishes whatever local `main` already points at, not your commit. Confirm the merge succeeded before pushing.
- This is a shared multi-worktree: local `main` can advance from another worktree mid-`cps`, so your ff-merge can suddenly refuse (diverged). Recovery: `git fetch origin`, `git rebase origin/main` your dev branch (disjoint files rebase clean), re-run the gate, then ff-merge + push. No force-push, nothing lost — the other commit is usually a sibling off the same base.
- Production pull/merge is `--ff-only`. Never edit, stage, or commit inside the production checkout.
- Restart is NOT part of `cps` itself. After code changes in a dev worktree, restart the active dev server before reporting ready; restart prod only when explicitly asked (see Restart workflow above), then verify `/api/ping`, the process cwd, and `YOLOMUX_VERSION`. The login page may not expose the version to unauthenticated curl; do not rely on a blank version grep alone.

## How The Webterm Works

The server is a dependency-light Python `ThreadingHTTPServer`. It serves one HTML page, local xterm.js assets, JSON APIs, Server-Sent Events streams, and a WebSocket endpoint.

For each terminal connection, the browser opens `/ws?session=<tmux-session>`. The server creates a PTY, runs `tmux attach-session -t <tmux-session>` for admin users or `tmux attach-session -r -t <tmux-session>` for readonly users on the PTY slave, reads terminal bytes from the PTY master, and sends those bytes to xterm.js as WebSocket binary frames.

Closing the WebSocket before the initial resize payload is an expected disconnect. `bridge_tmux()` returns before PTY allocation for that case and uses the same `OSError` family boundary as later terminal disconnects, so reloads cannot emit request-thread tracebacks or allocate an orphan PTY.

Browser input is sent as JSON messages over the same WebSocket. Normal keyboard data becomes `{"type": "input", "data": "..."}`. Resize messages become `{"type": "resize", "cols": ..., "rows": ...}`. Scroll messages become `{"type": "tmux-scroll", "direction": "up|down", "lines": ...}`.

Terminal image paste is latency-sensitive. The browser upload path inserts the `[Image #N] <path>` reference from the `/api/upload` response, repaints the terminal, and may refresh upload/event UI, but it must not force a transcript/session-metadata refresh. Upload-directory resolution is static and authenticated-user scoped: `/tmp/yolomux.<login-user>/uploads/<session>/`; it must not inspect the session cwd, discover agents, resolve transcripts, or trigger macOS `lsof` process scans. The per-user root is verified as a non-symlink directory owned by the server's Unix uid before it is secured to `0700`; files are reserved with exclusive creation for multi-server safety. On macOS, general agent cwd discovery uses `libproc.proc_pidinfo(PROC_PIDVNODEPATHINFO)`, while Codex transcript attribution enumerates open vnode paths with `PROC_PIDLISTFDS`/`PROC_PIDFDVNODEPATHINFO`. A native lookup failure emits a deduplicated server warning and falls back to a bounded, TTL-cached `lsof` query; do not restore an unconditional all-process or all-file-descriptor scan.

Resizing is handled on the PTY slave file descriptor, then the server sends `SIGWINCH` to the tmux attach process group. The browser sends resize updates only after a debounce, except for an initial fast resize during WebSocket startup.

The browser creates panel DOM nodes for visible sessions at boot, checks that the backing tmux sessions exist, and starts terminal connections for them. Visible layout changes move existing panel nodes into slot containers. Hidden panels move back to `#panelPool`. This keeps xterm instances and WebSocket connections alive while changing layout.

The full layout is encoded in the page URL through readable `sessions`, `layout`, and `tabs` query parameters; split positions are stored as percentages in `layout`. This makes a layout reload-safe and shareable/bookmarkable without browser storage.

Transcript metadata comes from tmux pane discovery plus local process-tree inspection. ### OpenCode support boundary

OpenCode support is limited to the installed and captured `1.18.25` visible TUI shape. The native executable must be validated as the real `opencode` process before its pane text is classified; shell output, command arguments, child tools, and arbitrary text containing `opencode` do not create an agent row. Three sanitized read-only captures are registered in `tests/fixtures/prompt_corpus/captures/inventory.yaml`: `completed_output` proves an idle bordered multiline composer with `Ask anything...` and a `Build` provider/model footer, `working_coordinator` proves the filled activity meter and `esc interrupt`, and `working_tool_wrap` proves a current tool row with extra-indented wrapped values. These captures were taken at approximately 101-106 columns, not the queue's canonical 200x40 capture size, so width-variant logical-line preservation remains unproven.

OpenCode state rows use the shared visible `working` and `idle` states from the existing pane classifier. A visible unsupported question or permission shape is non-typeable and must not be treated as a Claude/Codex approval; no real OpenCode question or `Permission required` capture is available in the current corpus. The existing right-click path preserves OpenCode's native `Copy`, `Copy without indent`, and `Copy tmux selection` behavior through an exact-pane capability check, while the YOLOmux terminal context menu remains for Claude/Codex. No exact browser test currently proves OpenCode split-pane targeting, selected indented text, or long wrapped values.

OpenCode usage reads are read-only and credential-free. The default database path is `~/.local/share/opencode/opencode.db`; the reader uses bounded explicit columns from `session`, `message`, `part`, and the state-only `session_input` table, never opens credential-bearing fields, never reads the WAL directly, and never uses SQLite as a control transport. `step-finish` owns completed token snapshots and `message` rows are identity/context only. The reader reports input, cache-read, cache-write, output, reasoning, provider, model, timestamps, and cost as available machine fields; current YO!stats atoms emit only the exact input, cache-read, and output roles, so reasoning and cache-write remain partial/omitted rather than fabricated. Missing, locked, malformed, incompatible, ambiguous, and mismatched sources become typed unavailable spans, and counter cursors use receipts and epochs for revised or reset snapshots.

OpenCode is not a structured YO!agent backend in this release. It has no native session-resume/send integration through YO!agent, no auto-approval or permission-action path, and no managed HTTP/SSE endpoint in the existing default TUI. The default captured process exposed no attachable listener; `opencode serve`, explicit loopback HTTP/SSE, and ACP are separate future integration boundaries and must not be inferred from the local SQLite database. YO!agent sends and wait-then-send jobs therefore continue to target only Claude/Codex panes, and OpenCode permission UI remains blocked rather than auto-approved.

The transcript tab uses Server-Sent Events from `/api/context-stream`. The AI summary tab uses `/api/summary-stream`, which builds a scoped prompt from the selected session's recent transcript and streams a Codex-generated summary back to the browser. Summary provider defaults live in `settings.yaml` under `summary.*` and in the backend settings catalog; `YOLOMUX_SUMMARY_MODEL`, `YOLOMUX_SUMMARY_EFFORT`, and `YOLOMUX_SUMMARY_SERVICE_TIER` only seed defaults when they name valid catalog values.

YOLO uses `tools/auto_approve_tmux.py` workers behind `/api/auto-approve`. The browser polls YOLO status every `paneStateRefreshMs` and reflects the active state in each pane tab.

Native `watchfiles` events wake this path but do not eliminate reconciliation: the elected owner still calls `watch_signature(..., child_limit=512)` for each watched root, and that helper may inspect up to `MAX_DIRECTORY_ENTRIES` (1,000) visible names before retaining the first 512 in the signature.

Each process keeps browser-requested file watches in one `ClientWatchFileRecord` per normalized path. The record owns both the TTL expiry and the mutually exclusive active/background mode. `POST /api/watch/roots` replaces that record set atomically, and active/background signature consumers derive their sorted path lists through one expiry-pruning helper. Do not reintroduce separate active and background maps: overlap repair and duplicate expiry paths previously let the same path occupy two modes.

## Multi-host shared-home implementation status

### Legacy database adoption

Partitioned stores deliberately do not migrate legacy unpartitioned databases. Automatic adoption cannot prove which host produced a file that both hosts can see. Search and pricing are reconstructible and should rebuild; login-throttle state normally starts fresh; stats history may be adopted only for a confirmed source host. YO!chat uses its independent host partition now: old messages, dated history, and the cursor key remain at the legacy paths and do not appear in the new room.

For a manual stats adoption, stop every source/target writer, keep the legacy database and sidecars untouched, run `sqlite3 -readonly "$legacy_db" 'PRAGMA quick_check;'`, create a consistent backup with `sqlite3 "$legacy_db" ".backup '$backup_db'"`, and require `sqlite3 -readonly "$backup_db" 'PRAGMA integrity_check;'` to return `ok`. Resolve the destination identity in the launch environment with `python3 -c 'from yolomux_lib.infra.host_identity import current_host_identity; print(current_host_identity().stable_host_id)'`, require an empty `STATE_DIR/hosts/<stable-host-id>/` target, and populate it through SQLite's backup API rather than copying the database/WAL/SHM files independently. Keep the source and validated backup for rollback; never delete or merge a foreign host's files.

### Shared physical worktree protection

One declaration parent, `infra.worktree_writer`, protects source-mutating tools in a shared physical Git worktree. Its record lives at `<gitdir>/yolomux/worktree-writer/owner.json`, not in the source tree, and consumes `HostIdentity.process_record_fields()` plus the display hostname, purpose, random ownership token, declaration time, and heartbeat. The owner refreshes every five seconds. Owned release is token-checked; a same-host dead/recycled/previous-boot record is reclaimable immediately, while a foreign or otherwise unverifiable record remains active until its heartbeat is more than 30 seconds old. A stale owner's later cleanup cannot remove a successor record.

Normal servers detect and warn on a fresh foreign or unverifiable declaration, then continue as read-only source consumers. They never create, refresh, reclaim, or release the declaration and never refuse startup on this evidence. Writer tools have stronger evidence because they declare their own intent: `tools/check.py`, direct pytest, and `tools/static_build.py` refuse writer tools while a fresh owner exists. Use `python3 -B -m yolomux_lib.infra.worktree_writer --purpose <purpose> -- <command>` for an explicit source/Git-mutating command that has no built-in integration; `-B` suppresses the first package cache until the module installs the host-local prefix. Arbitrary editors, Git clients, package builders, and third-party tools cannot be intercepted centrally; use that wrapper or a separate physical worktree.

Known future ordering consideration: a queued writer tool can hold its writer declaration while waiting for the expensive-tool lock. Do not change this behavior during normal operation; any future lock-order change should acquire the expensive-tool lock before the writer lease, so writer exclusivity covers only the actual writer phase.

Supported worktree entrypoints suppress bytecode before the first `yolomux_lib` import; package initialization then installs `PYTHONPYCACHEPREFIX` and enables later imports below the host-local root. This bootstrap is required because Python chooses the package's own cache destination before executing `yolomux_lib/__init__.py`; package code cannot retroactively relocate that first cache. Pytest routes `.pytest_cache`, and pip/npm caches plus coverage output live below a per-worktree digest in `YOLOMUX_HOST_ARTIFACT_DIR`, `YOLOMUX_RUNTIME_DIR`, `XDG_RUNTIME_DIR`, or the per-UID `/tmp` fallback. That selected base must be host-local. Uploads already use `/tmp/yolomux.<user>/uploads/`, boot logs default to `/tmp`, and existing runtime roots carry sockets/leases/locks. Checked-in generated static files stay in the checkout and are protected by the writer declaration because relocating them would change the source/build contract. Package metadata, wheel/build directories, browser profiles, and arbitrary external tool output need explicit host-local output directories. `GIT_OPTIONAL_LOCKS=0` prevents read-only Git commands from refreshing the shared index implicitly.

Expensive background coordination is single-owner per local `YOLOMUX_STATE_DIR` on one host, while durable stateful work is owned by local services in separate PIDs. `STATE_DIR` defaults to `~/.local/state/yolomux`; setting `YOLOMUX_STATE_DIR=/some/path` makes every YOLOmux process on that host that uses the path share the same coordination files, caches, locks, service sockets, and service-discovery records. The background-owner election files live under `STATE_DIR/background-owner/`: `owner.lock` is the global flock, `owner.json` is the current owner heartbeat/status record, and `generations/*.json` are live process generation records. The latest live generation owns Tabber activity refresh, session-files refresh demand, watch-root polling, and independent YO!stats metric workers; older servers become followers even if a browser is actively connected to them. Followers serve shared ready/stale snapshots and request refresh from the owner over the control socket. Token-consumer demand is a family-specific owner refresh that wakes only the token worker; there is no statsd-to-web sampling RPC. Followers must not start warmers, metric workers, or derived watch-root directory polling/listing. They still update the same-host watch-root intent index at `STATE_DIR/watch-index.json` so the owner can observe connected browser interest.

Retained history durability is a property of the root, not an unconditional guarantee. The primary port (7770 on Linux, 8880 on macOS) runs against the durable default root `~/.local/state/yolomux`, so its statsd database, service records, and other retained state survive a restart. Every non-primary (dev) port is relocated by `tools/instance_isolation.py` to an ephemeral per-UID `/tmp` root (`<tmpdir>/y<uid>/p<port>`) and is ephemeral by design: its retained history is discarded whenever `/tmp` is cleared. The "History retained since" row in the Daemons view reports how far back the current root's history actually reaches (the observer epoch start), so a reader never has to assume persistence that the root does not provide. This is a documentation distinction only; no code path adds or removes retained state to make one root behave like the other.

### Current token/cost recovery

Transcript discovery is an input to the atomic all-source migration, not a separate retained-bucket repair mode. The migration reuses the one transcript-to-usage-atom identity owner, deduplicates provider events, reconciles Agent/Model/Cost totals, preserves incomplete evidence as an explicit lower bound, and converts unreconstructable spans to current no-data. After the current schema activates, normal repair appends missing current usage atoms through statsd and invalidates the affected materialization generation; no tool may rewrite derived display buckets because the current database does not contain them.

Migration and current repair fail closed while another writer or incompatible daemon owns the state directory. They acquire the same service/writer fences, preserve a forensic backup, validate reconciliation before activation, and leave the active database unchanged on failure. The retired offline bucket wipe/rebuild path is not part of current serving or repair.

Local services share one lifecycle and RPC parent. `local_services/rpc.py` owns the versioned length-prefixed JSON envelope with optional bounded binary payload and rolling legacy newline reads. `local_services/runtime.py` owns `LocalRpcServiceState`, service-side mode-`0600` Unix socket binding, peer UID checks where available, singleton locks, response correlation, and idle cleanup. `local_services/registry.py` owns client-side discovery, stale PID/socket cleanup, `sys.executable -m <module> --serve` spawning, service records under `STATE_DIR/services/*.service.json` or next to the socket, exponential crash backoff from 0.25 seconds to 8 seconds, and lease-protected idle exit. A service failure may produce stale/pending/unavailable responses, but the web process must not run a retired expensive local fallback.

`statusd` owns the shared public session/agent-status snapshot: lightweight discovery, pane capture/classification, assembly, and encoded auto-approve bytes. Web routes only authenticate, validate, and forward that result; the watcher publishes an `auto_approve_changed` transition from its generation/status rather than rebuilding a roster. `approvald` remains the separate action-worker owner. Statusd accepts version-stamped public requests, serves a bounded stale complete snapshot or `503`/`upgrade_required` without a web fallback, and exposes `invalidate` plus bounded `wait_generation(after_generation, timeout)` for status consumers. Statusd also owns a separate, private `inventory` action: a versioned session-inventory contract carrying only bounded per-session identifiers and a `source_signature` (never git/transcript/repo/PR enrichment), with the DAEMON discovering the canonical tmux roster itself (`list_tmux_session_names`) rather than trusting a web-supplied session list as authority; a web-supplied roster is only a fallback when tmux enumeration fails. `inventory_generation` advances only when the discovered roster's aggregate source signature changes, so refresh products (batchd) can key work on a stable upstream generation instead of re-deriving topology themselves.

Web-owned refresh compute is being migrated to `batchd` as typed materialized products, not just stateless one-shot tasks. `BatchClient.product(coalesce_key)` returns the newest COMPLETED bytes for a product identity (`ready`/`stale`/`pending`/`none`) independent of whether a newer generation is still building, which is what makes stale-while-revalidate a broker property: a web route can serve a prior complete product while a newer submission runs, without ever falling back to in-process compute. The broker's existing `_submit` generation guard (an older-or-equal generation submission is coalesced into the existing job) and `_store_product` (a slower older-generation completion, or any failed/superseded completion, can never overwrite a newer complete product) together guarantee that a delayed result cannot regress a fresher one. `session_files_view` (registered 2026-07) was the first product built on this contract: the web owner submits the session's `SessionInfo`/options as JSON (never pickled — batchd workers run in a spawn `ProcessPoolExecutor` with no access to app state), the worker reconstructs the dataclasses, builds a per-task memoizing git-snapshot provider, and calls `session_files.session_files_payload(_for_info)` entirely inside the worker process. The web-side cache KEY for session-files uses the fs-watcher's per-repo dirty generation (`repo_dirty_generation`) instead of spawning `git status` to build a git-identity hash, so a warm request over an unchanged, watcher-covered repo performs zero git-identity spawns in the web process; an uncovered repo falls back to the spawn-based identity so freshness is never silently lost.

`tabber_activity_view` and `metadata_warm_view` (registered 2026-07-18, `BATCHD_PROTOCOL_VERSION` 4→6) follow the same impure-gather/pure-assemble split for the two remaining refreshers. For Tabber, `agent_window_gathered_agents` (app.py) does the impure per-agent gathering (live tmux screen capture, attention/cooldown keys, path/git) that cannot run in a spawn worker; `build_activity_payload` batches every session whose per-session signature changed into one `tabber_activity_view` submission, and the worker (`activity_summary.tabber_activity_view_result`) does pure dict assembly/sort only, reusing unchanged sessions' prior rows. The per-session signature folds in the statusd-owned roster row (not just tmux screen text) so a roster-only change still busts reuse. For metadata warming, `warm_metadata_cache` submits one `metadata_warm_view` job per session (not batched, to preserve per-session demotion-cancellation granularity); the worker runs `session_work_graph(info, fresh_cache, allow_network=True)` against a worker-local `MetadataCache`, snapshots every GitHub/Linear/git cache entry it populated as `{key: {value, ttl_remaining}}`, and the web owner replays those entries into its own long-lived `metadata_cache` via `.set(key, value, ttl=...)` — reproducing the same warm effect without the web process ever making a network call or git spawn itself. Both raise a dedicated `*BatchUnavailable` exception (never an inline fallback compute) so an unreachable broker serves last-known-good/stale data or simply skips a warm cycle instead of rebuilding in web.

Exact stats requests are bounded by the canonical matrix and service protocol. `GET /api/stats-snapshot` asks for one preset Range and `AUTO|1|10|60|300`; statsd returns one already-published generation with at most 600 uniform buckets or a structured `pending`, `unsupported`, `unavailable`, or `upgrade_required` result. A request never opens SQLite, runs a family fold, encodes a new body, or retries through another protocol. The browser keeps one generation-tagged loading/error owner, rejects stale or mismatched responses, and uses bounded retry/backoff without paging older ranges.

The elected app owns one non-overlapping deadline worker per metric family: CPU at 1 second, Agent Status/GPU/service load at 10 seconds, system memory/hardware at 60 seconds, and transcript tokens at 10 seconds while watched or 60 seconds while idle. Each worker appends only its original observation through the current statsd writer, and one slow or failed family advances/skips only its own deadline. statsd is the sole SQLite mutator and commits each append under `journal_mode = WAL` with `synchronous = NORMAL` (`yolomux_lib/stats_current/storage.py`), so a commit survives process loss immediately and survives power loss at the next WAL checkpoint (`wal_autocheckpoint` = `WAL_AUTOCHECKPOINT_PAGES`, 1000 pages). There is no separate per-family durable-write deadline and no test asserts one: CPU's one second is a collection deadline, so serving freshness is bounded by commit cadence rather than by a distinct durability budget. The materializer consumes committed generations asynchronously, recomputes deterministic dirty cells through the same fold as a full build, and publishes one immutable generation without blocking the writer/listener. `statsd.sampler_families` and materializer diagnostics expose cadence, attempts/successes/failures, late/missed, runtime, queue depth, warm/dirty state, generations, bytes, and last failure.

The current schema stores original per-family observations, usage atoms, coverage/epoch facts, unavailable spans, migration reconciliation, and schema/minimum-writer metadata. Adjacent sampler owner generations remain distinct; prefix, suffix, middle, multiple, and empty coverage shapes are ordinary data; absent samples remain no-data rather than zero. Derived `1s/10s/60s/300s` layers exist only in statsd memory. Counts, tokens, costs, and event rates are never held or repeated.

The web process CPU budget is below 10% when idle and below 25% with YO!stats visible on the standard macOS development host. The existing one-second CPU sampler owns enforcement: more than 30% process CPU sustained for five minutes emits one deduplicated `stats-cpu` warning with the three largest endpoint/background compute owners, and the System tab exposes current/budget/sustained values. This adds no monitoring timer. Metadata refreshes are process-wide single-flight: concurrent readers share one real status/signature check, and unchanged repositories reuse the full Git metadata snapshot instead of repeating branch, remote, worktree, and inventory subprocesses. A dirty worktree or a real ref change (`.git/HEAD`, `refs/`, `packed-refs`, `MERGE_HEAD`) invalidates and rebuilds; a repo's own `.git/index`/`*.lock` churn is NOT treated as an external invalidation, because `git status` itself rewrites `.git/index` on every read, and feeding that write back in made a compute bump the generation that then discarded its own result — a self-perpetuating refresh livelock — while the 15 s cache TTL backstops any staging-only change skipped. On a mid-compute invalidation the owner caches and returns the value it just computed and refreshes on the next call, rather than discarding it and recomputing inline. The single-flight aggregate (session-metadata) refresh worker carries a bounded deadline so a stalled build can be superseded instead of pinning the guard and freezing the header indefinitely. Concurrent Finder refresh owners may bypass the completed listing TTL with `fresh`, but identical in-flight directory listings still coalesce into one `/api/fs/batch`; explicit user freshness is preserved without multiplying enumeration.

Repeated visible-client token demand may shorten a stale 60-second idle deadline, but demand inside the active 10-second cadence is coalesced even after the previous scan has completed; UI polling therefore cannot create a token-scan wake storm.

Browser/client metric upload uses the bounded `POST /api/stats-observations` acknowledgement path with stable event identities, a server-bound client ID, and the current writer protocol/schema generation. statsd deduplicates and appends originals, then marks deterministic materialization cells dirty; the request never compacts history or returns a snapshot. Retention deletes only expired originals/atoms/coverage, and incremental/full materialization stays outside the request and writer/listener threads.

Terminal path confirmation and base file reads use batchd's bounded foreground point path. One user action creates at most one ordered candidate task; candidate paths do not fan out into parallel jobs. The broker caps each accepting instance at eight queued point jobs and two queued foreground jobs, caps the daemon at 32 queued jobs, keeps foreground work ahead of freshness and maintenance work, and threads one absolute deadline from admission through candidate probes, descriptor-pinned base I/O, optional Git, and publication. A deadline stops later cooperative phases and fences a late result from publication; it does not claim to interrupt a kernel-blocked filesystem syscall.

The file-open path is deliberately split. Candidate confirmation and the regular-file base read must complete without Git history, Git object-cache accounting, Blame, or Diff work. The browser can show base content while optional enrichment is pending, unavailable, oversized, or rejected. A busy Git cache reservation returns a typed pending/busy result instead of holding the base-read deadline on a lock. Batch status reports the accepting instance/state root, queue wait, active task and phase, per-worker resource rows, journal bytes, and file-backed artifact bytes so an operator can distinguish broker memory from one worker or product. Each lane owns independently replaceable one-worker slots, and deadline-backstop quarantine keeps at most two unreaped predecessors across the broker; do not add a parallel executor lifecycle owner.

`QueuedDeliveryLedger` is the sole durable queued-operation journal owner. It reads recovery input in 64 KiB chunks, caps individual records at 1 MiB, writes segments no larger than 16 MiB, and bounds one recovery slice to 16 MiB or two seconds. Structural and aggregate decoded-state limits reject malformed or amplification-shaped input before it can become a worker heap. A corrupt physical generation retains its digest and one recovery diagnostic, salvages valid earlier rows in order, and is claimed once across ports until that source generation changes; scheduler ticks do not retry the same poison forever.

Sampled background-refresh event logging keeps `count` and `last_emit_count` in one typed record keyed by `(event_type, role)` under one lock. First/every-N emission and `suppressed_since_last` are one transaction; do not split those counters into parallel maps.

In-process caches follow the same record rule. `StatsSampleRecord` owns the process/system CPU baselines and the short-lived sampled payload; `TranscriptsPayloadCacheRecord` owns transcript payload age plus its stale-while-revalidate flag; and `TabberActivityCacheRecord` owns activity payload age, the source signature that classifies that payload, per-session source signatures/rendered rows, and per-key refresh futures. Cache get/set/invalidate/refresh paths must update these records under their existing locks rather than adding parallel timestamp, payload, signature, row, future, or refreshing attributes. The Tabber warmer thread is a separate long-lived scheduler and stays outside the cached-value record. A warmer tick reuses unchanged session rows, rebuilds only invalidated rows, removes vanished sessions, and returns the existing payload without an all-session rebuild when the complete source signature is unchanged.

### statsd serving, rebuilds, and health

statsd owns cold serving from a bounded aggregate ring persisted beside the originals, one row per resolution and bucket at a fixed capacity per resolution. A restart serves from that ring rather than decoding retained history, so cold cost follows ring capacity and not store size. Buckets whose facts changed while nothing was running are recorded as owed in an invalidation ledger, and the first build after restart rebuilds exactly those cells. An unrebuilt bucket is never served as quiet zero.

Rebuilds are bounded by rows read, decoded bytes held, process memory, and lifetime, all at once. Work folds in bounded chunks and each decoded chunk is discarded after aggregation, so peak memory follows chunk size rather than row count. A build that hits any bound stops and leaves the rest owed; the next build continues from the ledger. Do not add a rebuild path that holds the whole decoded history, and do not replace the ledger with an in-memory work list — the ledger is what makes partial progress survive a restart.

**Measure a daemon's memory as `RssAnon + VmSwap`, never `VmRSS`.** RSS falls when the kernel swaps a process out, so a daemon can breach its budget and read healthy. On the live statsd, `VmRSS` reads **61.36% below `VmHWM`** while `RssAnon + VmSwap` reads **1.08%** below it: checked against RSS that daemon looks like 618 MiB and healthy while it holds 1,583 MiB. A figure quoted in RSS or USS is not comparable to the sum and has to be re-derived, not converted. Neither health path reports PSS or USS, because `/proc/<pid>/smaps_rollup` is their only source and reading it takes the target's `mmap_read_lock` for the duration.

`/readyz` and `/livez` are served by the web listener, and they are not interchangeable. `/readyz` requires authentication and reports whether statsd can serve a correct snapshot; `/livez` is public because `boot.sh` polls it before any operator cookie exists, and it answers only whether the process can make progress. Keep the detailed resource projection on `/readyz`. The public endpoint previously published `verdict.payload` whole — ten keys, six of them process detail: `pid`, run `state`, `cpu_ticks`, both IO byte counters, and `voluntary_ctxt_switches` — to unauthenticated callers, and now returns `{"ok": ..., "live": ...}` and nothing else. That is a security fix rather than a routing change, and it was found by reading `get_healthz`'s own contract, which is a rule about content: reporting anything richer would both leak system state to an unauthenticated caller and let an unrelated subsystem fail a restart. Do not widen `/livez` again. Do not add a second readiness definition when extending either one. **No live HTTP request has been made against either route.** Route resolution and dispatcher refusal are proven; end-to-end is not, because a listener could not be started under the measurement freeze. One `curl` against a running server upgrades this from proven-by-construction to observed. Both routes are implemented and not yet integrated: they are absent from the current candidate tree. They answer different questions. `/livez` asks only whether the process can make progress, and is computed from a `/proc` sample the caller reads, so it never enters statsd and never waits on the GIL the materializer holds across a build burst. It fails on an unreadable process, on a state outside `R`/`S`/`D`, or on no CPU and no context-switch movement past a stall window sized as a multiple of the daemon's own measured build time. An idle daemon is flat by definition and is never called dead. `/readyz` asks whether a correct snapshot can be served right now and fails closed: no positive `cache_generation`, any staged cell, a ring-writer failure, a failed materializer, migration not ready, a build failure since the last publication, or owed startup slots. It reports every failing condition rather than the first.

Do not wire readiness to `cache_ready_event`. On 6 of 6 cold starts that event fires while the served window's ring is still staged, and a snapshot at that instant is legitimately refused — measured at 1,248 staged cells at the readiness instant. Read staged cell counts, not the boolean queue-pending flag, which reads the same for one staged cell and for the whole ring. Neither endpoint may route through `_status()`, which takes the work lock the materializer holds across a build: a health check that blocks behind the daemon it is checking reports nothing.

Batched persistence exists and ships disabled, because the buffered overlay serves facts without advancing `source_generation` and advancing it for uncommitted facts would break "no cursor, watermark or generation leads durability". The collision is recorded at `service.py:59-77`; the follow-up owner is `queues/backlog/DOIT.p1.e4.statsd-batched-persistence-generation-key.md`. Do not enable it, and do not document how to.

Search-index files live under `STATE_DIR/hosts/<stable-host-id>/search_index/`. Each indexed root gets digest-named files: `<digest>.sqlite3` for entries, `<digest>.manifest.json` for cheap status/count metadata, `<digest>.lock` for the per-root build lock, `<digest>.tomb` for removals, plus SQLite WAL/SHM sidecars when SQLite needs them. The schema is `INDEX_FORMAT_VERSION=6`: the `entries` table carries a `generation` column, metadata binds the snapshot to the authorized root identity, and durable `directory_coverage` and `frontier` tables preserve per-directory breadth-first coverage and the pending queue across restart. Version 4 and 5 databases are rebuilt because they do not record the descriptor generation that produced their rows. Servers read the small manifest and committed SQLite snapshots; `indexd` is the only process that applies row deltas, full rebuilds, and unindex writes. Quick Open queries consume ready/stale data and do not schedule a TTL rebuild. When the background owner is elected, `app.handle_background_owner_acquired`→`refresh_search_indexer_schedule()` leases the configured roots on `indexd` (reusing the one `local_services/runtime.py::acquire_client_lease` owner) and enqueues a `startup-depth-1` item per root; reconciliation is delta-based (added roots enqueued, removed roots unindexed, unchanged roots untouched) and the lease is released on demotion or when the configured set empties. Configured-root full builds run through `bfs_index.build_root_into_index` (a breadth-first, directory-at-a-time frontier owned by `indexd`), not the recursive `_walk_root_with_metrics` DFS, which now survives only on the incremental dirty path and the no-runner fallback: layer 1 is one listing of the root that atomically publishes its direct files, deletions, and the layer-2 child-directory frontier, `published_depth` advances only after a whole layer is terminal, and a restart resumes the shallowest pending directory without recursive rediscovery. Concrete change evidence (native `watchd` revisions, YOLOmux write/delete/mkdir/rename/upload mutations, and visible Finder/Differ roots) routes through the one owner `filesystem/search.py::reindex_roots_for_paths`, coalesced by canonical directory with bounded per-root heat that decays after `HOT_INACTIVITY_SECONDS=90`; a starvation bound (`HOT_REPAIR_STARVATION_BOUND=8`) yields one lowest-priority `full-safety-refresh`. Because the lease keeps `indexd` alive, `file_explorer.index_refresh_seconds` (default 1800; the `SAFETY_REFRESH_REASON`/`full-safety-refresh` precedence class) now fires as a lowest-priority reconciliation independent of query or invalidation traffic, resumable and preemptible through the same frontier, and it never blanks the readable previous snapshot before replacement rows publish. Known caveats: a mutation driven through the full `POST /api/fs/write`→`batchd` chain did NOT refresh in-window for a root with no active indexer lease, so whether a batchd-executed mutation reliably RPCs `indexd` in a multi-server or follower topology is an open question; and the bounded read path reuses the existing 30-second SQLite connect timeout (live reads observed under 2 seconds) rather than a shorter read-path deadline. [`docs/specs/FS_INTERACTIVITY.md`](specs/FS_INTERACTIVITY.md) is the shipped contract for startup layer-1 publication, the breadth-first frontier, hot-path cadence, truthful coverage, and scheduled lifecycle; [`docs/DONE/2026-08/DONE.fs-interactivity.md`](DONE/2026-08/DONE.fs-interactivity.md) retains the implementation and 0.7.3 release evidence. In-memory entries, persisted entry count, and estimated/actual cache bytes are bounded; truncated or over-budget roots remain usable as explicit partial in-memory indexes and are not persisted. Recoverable SQLite writes are optional and debounced, while locks, tombstones, settings, and user data keep their existing durability. The default skip set rejects generic generated/dependency/build trees; `file_explorer.index_exclude_paths` adds machine/project-specific rules, one per line: plain absolute/home-relative subtree paths, `glob:<root-relative glob>`, or `regex:<expression>` against root-relative POSIX paths. Invalid regex rules are ignored, and the complete effective rule set participates in the index signature so policy changes rebuild rather than reuse incompatible rows. `/api/fs/index-status` and the runtime report expose build/full/incremental counts, last duration, scanned/ignored entries, dirty subtrees, truncation, cache bytes, and write bytes, plus a per-root `progressive_coverage` object read through the one bounded owner `file_index.read_index_coverage` (live SQLite metadata mid-crawl tagged `source: live`, atomic manifest fallback tagged `source: manifest`, 50-millisecond busy timeout) carrying active/published generation, published depth, frontier depth/size, full-coverage completion, snapshot age, and last progress; `runtime_status()` reports measured configured-root obligations with the scheduled-absence reason `configured_roots_scheduled` instead of a hard-coded demand-only idle. The browser keeps `/api/background/status` fresh so the top-right ownership chip can show whether this connected process is the background owner/follower, while `--print-runtime-report` shows the actual `indexd`, `statsd`, `batchd`, and `approvald` service rows. `background_owner_changed` pushes update that status after election changes, and the status is refreshed on EventSource reconnect and manual refresh.

If the owner heartbeat/control socket is stale but the flock is still held by a live process, a follower must not steal ownership because that would split coordination; it may run only the existing bounded immediate-response fallback and then return to follower mode. Local service ownership remains guarded separately by service locks and SQLite single-writer rules, so owner failover must not create a second `statsd` or `indexd` writer.
