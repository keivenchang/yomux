# 2026-07-18 Offload web refreshers to jobd

- Completed and removed `DOIT.offload_web_refreshers.md`. Each `yolomux.py` web daemon now stays focused on authentication, request validation, routing, and forwarding already-built responses; transcript, session-files, Tabber, and metadata refresh compute moved into `jobd`, one shared bounded work owner, so periodic refreshes no longer create web CPU spikes and every local port reuses the same materialized results. `jobd` gained a materialized-product layer (canonical bounded keys, dependency/source generations, priority, single-flight/coalescing, last-known-good immutable bytes, stale/pending/unavailable responses, per-product counters) beside its existing stateless job API, and `statusd` gained a private versioned session-inventory contract other products key work on. Registered products: `transcript_view`, `session_files_view`, `tabber_activity_view`, `metadata_warm_view` (`JOBD_PROTOCOL_VERSION` progressed 3→6 across the migration, one bump per new task).
- Session-files, transcripts, and Tabber each follow the same impure-gather/pure-assemble split: live tmux/git/GitHub/Linear state is gathered in the web owner (or inside the jobd worker when the source is itself stateless, like git spawns/network fetches), then only pure JSON assembly runs in a jobd spawn worker. Session-files' cache key uses the fs-watcher's per-repo dirty generation instead of a `git status` spawn, so a warm request over an unchanged, watcher-covered repo performs zero git-identity spawns. Tabber batches every session whose per-session signature changed into one submission per `build_activity_payload()` call, reusing unchanged sessions' prior rows; that signature folds in the `statusd`-owned roster row (not just live tmux screen text) so a roster-only change still busts reuse. Metadata warming (GitHub PR / Linear issue / git-branch enrichment) submits one `metadata_warm_view` job per session — not batched — specifically to preserve the pre-existing per-session demotion-cancellation contract, then replays the worker's materialized `MetadataCache` entries back into the web process's own cache. Every migrated path raises a dedicated `*JobdUnavailable` exception rather than falling back to inline compute, so an unreachable broker serves last-known-good/stale data (or skips a warm cycle) instead of rebuilding in web.
- Web-owned refresh scheduling turned out to be mostly already event-driven rather than browser-polled: the pre-existing server-side watch loop already routed filesystem/transcript-identity changes and explicit `force=True` refreshes through the same jobd products, with cross-port coalescing inherited from jobd's existing generation-guard `_submit`/`_store_product` invariant (an older-or-equal-generation submission can never overwrite a newer complete product). Auto-approve/status compute was fully retired from web (routes through `statusd` generations; `approvald` keeps actions/target locks); the System view's Local services table exposes `jobd` queue depth, generations, cache bytes/age/staleness, accepted/coalesced/superseded counters, per-product runtime totals, and renamed "Servers" to "Daemons" throughout.
