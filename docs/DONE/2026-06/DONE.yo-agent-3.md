## DOIT.67 YO!agent structured transports and central orchestration
- Completed and removed `DOIT.67.md`. YO!agent now has a transport-aware backend model for managed Claude/Codex work instead of treating tmux paste as the only send path: `claude-sdk`, `claude-channels` diagnostics, `claude-stream-json`, `codex-sdk`, `codex-app-server`, `codex-mcp-server`, `codex-exec`, and labeled `tmux-legacy` are represented in the transport registry with explicit capabilities and result-source metadata.
- Codified the durable research conclusion: arbitrary already-open Claude/Codex TUI panes do not expose a supported structured prompt-injection/result API, so robust orchestration must own the session lifecycle, start an opt-in control channel, or use provider SDK/app-server/MCP/exec protocols; visible panes without that protocol remain a terminal-automation fallback and must be labeled as such.
- Added persisted YO!agent job/result metadata for transport debugging, immediate managed-transport result recording, managed-target routing through the registry, structured Codex SDK/app-server/MCP/exec prototypes, a working Claude stream-json fallback for local managed Claude jobs, and lifecycle-based final-result watcher coverage so first assistant text before tool use is not treated as final.
- Documented the UX contract in `README.md`, `docs/DEVELOPMENT.md`, `docs/specs/GUI.md`, and `docs/YOAGENT.md`: SDK/app-server/MCP/exec targets are background YO!agent-managed sessions unless a real TUI/PTY exists, visible tmux panes use `tmux-legacy`, and YO!agent remains the central orchestrator for multi-session handoffs unless the user explicitly asks for relay/chaining.
