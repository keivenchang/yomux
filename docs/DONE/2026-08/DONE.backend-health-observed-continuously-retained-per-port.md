- M0A — statsd could poison its own service record and never recover. After `healthy()` succeeded, `ensure_started()` wrote a record built from a second, unvalidated `status` RPC; a missing PID was coerced to `0` (`local_services/registry.py:1055-1066`) while the call still returned `True`, and `may_remove_stale_record` (`infra/host_identity.py:317-321`) allowed only `process_not_found`/`process_identity_reused`, so the `invalid_pid` record was a permanent wedge behind `statsd start blocked by remove_stale_record`. Measured repro on `bba47f31e`: `first=True`, `record_pid_after_ping_status_race=0`, `second=False`. Fixed as one shared six-service lifecycle rule, not a statsd patch: every record publication routes through one validator requiring `ok`, the exact service/protocol, `pid > 1`, and a usable process-start identity; a same-host/same-boot `invalid_pid` record is reclaimed as record-only cleanup with zero signal, adoption, or socket action; a failed post-ping status invalidates health and continues through bounded retry instead of reporting success. Red regression added to `tests/test_local_services_launch.py`; all six clients and both `_CurrentRegistry` overrides audited.
- M0B — live `GET /api/fs/watch-diff?full=1` returned HTTP 500 because the accepted 65-128 root range failed by construction. `CLIENT_WATCH_ROOT_LIMIT = 128` upstream met the per-job `MAX_BATCH_REQUESTS = 64` downstream, and the resulting 400 was itself malformed: its `common.error_payload(canonical=True)` omitted the required causal stack, so the response parent rejected it and dispatch emitted `failed API response has invalid HTTP status or error shape 400`. Two fixes, both in the existing owners. Response contract: `canonical=True` now rejects an empty or invalid causal stack at construction, each route-aware caller supplies its exact `server.http` frame, and the same missing-frame sibling in `submit_filesystem_batch_operation()` was fixed in the same change. Capacity: `accept_filesystem_watch_diff_operation()` stays the sole HTTP receipt owner, `submit_filesystem_watch_batches()` became the sole deterministic partition owner splitting the sorted root list into consecutive chunks of at most 64, and `complete_filesystem_watch_diff_operation()` stays the sole submit/resolve/merge owner under the existing deadline/cancel fence. The 128-root contract was not lowered and no root is truncated. Registered-route red regressions were added first — the pre-existing direct-app test at `tests/test_app.py:8204-8225` never went through the route and was false-green for the live failure.
- M1/M2 — froze the real service catalog and settled how a demand-scoped service is observed. One focused test pins exactly the six names in the `app.py` inventory literal plus `ESSENTIAL_LOCAL_SERVICES`, records demand/status/identity/metrics owner and recovery eligibility per service, asserts the abandoned `daemon`/`storaged`/`SUBSYSTEM_SPECS` names are absent, and asserts no resource has two owners for one role (`tests/test_gate_panels.py:12,227` already pinned the six ids and the literal). `watchd` uptime and identity are now a registry-derived projection read from the persisted process record with **no** RPC: calling `WatchClient.runtime_status` would demand-start a demand-scoped service from a diagnostics path, so it remains deliberately uncalled. Proven by test for `statusd` and every other demand-scoped service.
- M3/M4 — one collector, one observer, no second sampling loop. `runtime_local_services()` was extracted behind a collector with an immutable snapshot schema preserving every bounded field and `schema_version` before any loop was added. The observer's relationship to the pre-existing `service_load` stats collector was decided in writing rather than left to accrete, because two sampling loops over one projection is this repo's dominant defect shape. The observer starts in `cli.py` after the port lease and stops before backend clients close, runs on `BACKEND_HEALTH_OBSERVE_SECONDS = 2.0` with a `BACKEND_HEALTH_PROBE_TIMEOUT_SECONDS = 0.5` per-probe bound (`yolomux_lib/backend_health/observer.py:146-147`, pinned at `tests/test_backend_health_observer.py:883-884`), and uses an injected clock and wake event rather than sleeps. Proven: start-once, wake, stop/join, no thread leak after app close, no dependence on browser/SSE/panel demand or the stats-collector role, two-sample debounce with immediate hard-failure transition, typed `starting`/`unknown` before the first completed observation, and — the mandatory clause — that a full observation cycle starts zero demand-scoped services.
- M5 — the port-scoped retained store: one file per leased web port at `STATE_DIR/backend-health/<port>.json`, written only by that port's observer under the port lease, using the existing `atomic_write_text` + `file_lock` owners. Explicit schema version, observer epoch, monotonically increasing revision, per-resource current state, cumulative aggregates, and at most 128 transition rows per resource, each row carrying revision, wall time, previous/new state, bounded reason code, verified process epoch, and recovery outcome — no payloads, paths, command lines, tokens, sockets, or child log text. Counters accumulate from deltas inside one verified `(pid, process start time)` epoch; an epoch change starts a new baseline and increments restart count only after a prior verified process existed. Rollback, missed final samples, or corrupt peer data marks coverage `partial` — never a negative delta or an invented count. A corrupt file is quarantined once, starts a new epoch with reason `history_corrupt`, and emits one deduplicated diagnostic. A write or fsync failure keeps the previous good snapshot and never reports success.
- M6 — per-service request/completion/error counts and latency, from measurements that already existed and were being discarded. `LocalRpcEnvelope` carried `service_duration_ms`/`queue_wait_ms`/`queue_depth` stamped in `run_local_rpc_service`, and `LocalServiceClient._request_once` computed `client_elapsed_ms` and then dropped the whole envelope on success, using it only to fill a `TransportFailure`. One common retained aggregator now owns accepted/completed/error/latency for all six services and publishes bounded cumulative count/total/max; average is `latency_total_ms / completed_count` and no individual sample is stored. jobd's pre-existing internal `request_counters` was routed through the one owner rather than left as a second copy. Concurrent accounting tests prove exact totals under success, rejection, expiry before and after the handler, transport failure, process restart, and observer probes — probe traffic is counted separately and excluded from the user-work aggregate.
- M7 — non-destructive recovery on top of the validated M0A lifecycle, wired and reconciled clause-by-clause on `8c348dd96` with 45 focused tests. A verified-down service schedules the existing `LocalServiceRegistry.retry()` primitive after 1, 2, 4, then at most 8 seconds, one attempt per backoff boundary, fenced by the existing latched `_terminal_failure`/`_upgrade_required`/`next_start_at` state. Identity mismatch, revision mismatch, `upgrade_required`, and demand-started-and-legitimately-absent perform zero mutations and expose the exact blocked reason. Asserted: zero automatic `stop`, `restart`, signal, destructive socket unlink, process reclaim, or adoption.
- M8/M9/M10 — the health reached the user without adding a poller or a second endpoint. `/api/system-status` rows gained snapshot revision/age, typed state and reason, history, aggregate coverage, restart/error/request counts, and mean/max latency, with `schema_version` bumped because `85_debug_panel.js:7792` guards on it and all current bounded fields preserved. `backend_health_changed` was added to the existing `core` client-event contract (`client_events.py:25`, `:67`, retained at `:105`) delivering `{epoch, revision, overall_state, degraded_resources}`, replayed on ready/reconnect, coalesced latest-per-resource, carrying no history or private detail, and generated while System and YO!stats are hidden. The existing `syncBackendHealthIndicator()`/`backendHealthState` owner in `10_core_utils.js` was extended rather than duplicated: one `role=status` indicator in `.topbar-right-tools` combines web transport and service health with precedence web-disconnected over service-down over service-degraded, names the affected resources, stays visible until a newer healthy revision satisfies the recovery debounce, and offers a details action into the existing System view.

- **Correction that cost real time — the retained history works and was wrongly reported as broken.** An earlier report concluded the per-port history had never been written on a live instance. That was wrong, and the mistake was looking under `~/.local/state/yolomux/`: **non-default ports are managed instances whose state root is auto-derived under `/tmp`.** The real file is `/tmp/y1776734304/p7771/state/backend-health/7771.json`, measured twice and advancing — 36,422 bytes at revision 131 under `writer.pid` 1085735, then 42,559 bytes at revision 156 under `writer.pid` 2336352, with `schema_version: 1`, `port: 7771`, `history_coverage: "full"`, all six resources present, and `persistence.total_failed_publications: 0`. A different pid at a higher revision proves the revision counter and the process-epoch handoff both survive a real restart, not just a test.
- **Consequence, undecided and carried forward:** because that state root is under `/tmp`, backend-health history for every non-default port does **not** survive a host reboot or a tmp sweep. The queue's "history must survive both service and web restarts" goal holds; surviving a reboot does not. This follows from the instance-isolation design and is not a bug, but nobody has decided whether it is acceptable — either accept `/tmp` retention for non-default ports and say so in the docs, or give managed instances a durable state root outside `/tmp`. Tracked in `DOIT.p0.v0.7.2.md` F3; do not carry it silently as debt.
