- Item 4 — the two noisy producers were reproduced and classified honestly, without hiding a real failure. watchd's repeated `terminal_failure` was a MISCLASSIFICATION: the reducer `observed_health()` collapsed a transient running-degraded reconnect window (pid>0 with `healthy=False` or a recorded `last_failure`) into the SAME latched token the registry uses for a permanent start-failure fence. A running process cannot be terminally failed. Fix in the one vocabulary owner: added a distinct `service_unhealthy` reason to `BACKEND_HEALTH_REASON_CODES` (`yolomux_lib/backend_health/store.py:216`) and had the running-degraded branch emit it (`yolomux_lib/backend_health/observer.py:325`, constant at `:184`). The STATE stays `degraded` — the warning is preserved, nothing is hidden — and the genuine not-running latched `terminal_failure` → `down` fence and its recovery block (`recovery_blocked_cause`) are untouched. statsd's 0.5s `probe_timeout` was CONFIRMED CORRECT and left unchanged: the observer's `BACKEND_HEALTH_PROBE_TIMEOUT_SECONDS = 0.5` is 6x tighter than statsd's own `STATUS_TIMEOUT_SECONDS = 3.0` status RPC, so an alive-but-loaded statsd is honestly reduced to `unknown`/`probe_timeout` (never `down`) and the 2-observation debounce already swallows a single miss; raising the timeout or lengthening the debounce is exactly what the DOIT forbids.
