# DOIT.p2.e5.js-framework.md - JavaScript Framework, Virtualization, And Desktop-Shell Decision

## Goal

Decide whether YOLOmux should adopt Preact, SolidJS, or Vue for defined UI surfaces; determine where scrolling needs virtualization and DOM-node reuse; and separately decide whether a Tauri desktop shell would provide enough value over the browser application. The behavior-preserving frontend cleanup, state-owner consolidation, file decomposition, shared renderers, lifecycle scopes, and native architecture improvements are already archived in `docs/DONE/2026-08/DONE.0-7-4-behavior-preserving-architecture-cleanup.md`; this queue owns decisions that may add a framework, change rendering architecture, or introduce a desktop shell.

## Context

- The current application uses no React/Vue/Solid/Preact application framework. Python renders the shell and bootstrap JSON, while numbered files under `static_src/js/yolomux/` share one global scope and are concatenated by `tools/static_build.py` into `static/yolomux.js`.
- Measured on `dev/0.7.2` at `9d6899d46`: the registered `static_src/js/yolomux/*.js` files total 82,454 lines and the generated `static/yolomux.js` is 3,793,845 bytes. `00_bootstrap_state.js` alone has 536 mechanically counted top-level `let`/`const` declarations; that count is a complexity signal, not a claim that all 536 are mutable application state.
- Focused libraries already own specialized widgets: Dockview Core for panel layout, xterm.js for terminals, CodeMirror 6 for editors and merge views, Marked/Highlight.js for Markdown/code rendering, and Mermaid for diagrams. YO!stats charts are custom SVG. A framework decision must preserve or simplify these integrations rather than wrap them in duplicate lifecycle owners.
- Browser state changes arrive through bootstrap JSON, `fetch`, WebSockets, EventSource/SSE, queued-operation receipts, local user actions, and persisted URL/settings state. The current question is not only how HTML is rendered; it is who owns each state transition, how subscribers learn about it, and how stale or reordered work is rejected.
- Existing reuse is partial: CodeMirror virtualizes its document, Dockview can reuse existing panels, Changes/Differ indexes and reuses some DOM sections, and Chat uses `IntersectionObserver` for older-page loading. This does not establish that Finder, Differ, Tabber, Logs, Graphs, Agents, session lists, or other long scrollers are virtualized or reuse row elements.
- Tauri and Electron are desktop shells, not JavaScript state frameworks. A Tauri decision must be evaluated independently from Preact/SolidJS/Vue and must account for the existing Python server, tmux/PTY control, local filesystem access, authentication, SSE/WebSockets, and cross-platform packaging.
- The current frontend/state inventory, native-store/facade design, shared lifecycle resources, Debug-panel decomposition, preview strategies, row/control builders, CSS-token cleanup, and source-test decoupling shipped through the archived 0.7.4 cleanup. Do not duplicate or reopen that implementation here.

## Gotchas

- Framework choice, state management, virtualization, and desktop packaging are four separate decisions. Do not claim that Tauri fixes browser state, that Redux requires React, or that a reactive renderer automatically virtualizes long lists.
- Prefer less code and fewer owners. A framework is justified only if the measured production path becomes easier to understand, test, and extend; adding adapters around unchanged global state is a regression.
- Preserve DOM identity where external libraries or user interaction depend on it. Recreating xterm, CodeMirror, Dockview panels, focused controls, selected rows, or active drag targets can lose terminal history, editor state, focus, selection, scroll, and subscriptions.
- A lower initial-render time is not enough. Stale-event rejection, unavailable/error rendering, hidden-panel delivery, subscription teardown, and repeated-update memory must be tested.
- Do not use a CDN or introduce an unpinned runtime dependency. Any accepted framework and build tool must be reproducible from pinned local inputs and served through YOLOmux's existing cache-busted static-asset path.
- Do not hand-edit `static/yolomux.js`. Edit source partials and use `python3 tools/static_build.py`.
- The retired collaboration feature remains quarantined. Do not expand this study into its revival; only identify migration constraints that would otherwise make a selected framework incompatible with the retained quarantine boundary.

## Done Criteria

- Every original question has a plain-English answer: what framework exists today, whether a framework should change, how state is owned and delivered, whether Redux or another store is warranted, whether SolidJS/Preact/Vue improves the representative path, which scrollers virtualize/reuse elements, and whether Tauri solves a named product need.
- The recommendation is based on the same fixtures and recorded measurements, not popularity, syntax preference, or a toy demo; every rejected candidate has a concrete reason.
- Any framework recommendation consumes the cleanup queue's one-owner state contract, has explicit generation/error/teardown behavior, and creates no parallel legacy/framework copy; `KEEP_NATIVE` creates no cleanup implementation in this queue.
- Every large scrolling surface has a measured current verdict and either a proven budget-compliant implementation or a named virtualization task with preserved focus/selection/accessibility/scroll contracts.
- A framework migration, if recommended, is divided into independently releasable slices with a first surface, compatibility boundary, rollback, tests, bundle budget, and explicit approval gate before production dependency changes.
- A Tauri/Electron decision is recorded separately and does not block the JavaScript/state recommendation unless a measured desktop requirement makes the frontend execution environment materially different.
- The editor extension/plugin decision records one literal `NO_EXTENSION_API` or `PROCEED_WITH_SEPARATE_QUEUE` outcome, names the motivating capability and trust boundary, and adds no production plugin runtime in this decision queue.
- Research-only completion changes no production runtime. Any later implementation must pass focused source/build/browser checks and the canonical `python3 tools/check.py` gate on a frozen candidate before it is called ready.
