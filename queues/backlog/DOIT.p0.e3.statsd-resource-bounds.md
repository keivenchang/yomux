## The tension this consolidation exists to resolve

The disk finding and the memory finding pull in opposite directions on the same two settings, and while they lived in separate queues each was free to state its half as settled.

- The disk scope finds `cache_size` and `mmap_size` are never set, so SQLite's 2 MB default applies to a 503 MB store, and proposes raising both.
- The memory scope measured `mmap_size` at zero with file PSS of only 0.2 MiB against 560.8 MiB of anonymous PSS, and warns: do not change mmap or cache size to fix statsd RSS without first reproducing the Python object graph.

Both are correct and they are not about the same thing. Raising the cache attacks physical IO and costs resident memory; the memory warning says a larger cache cannot fix an anonymous-memory problem caused by whole-history decoding. **Neither may be changed without measuring the other in the same run.** Any candidate must report physical write per fact, `syscr` rate, and peak/steady PSS/USS together, and state the trade taken. That single requirement is why these were merged.

### Cause A0: an hourly `VACUUM` rewrites the database with nothing to reclaim

The audit measured an unguarded hourly `VACUUM` writing **652,726,272 bytes (652.726272 MB)** while compacting a 225 MB copy, confirmed by `/proc/self/io` around the exact WAL/NORMAL/1000-page pragma sequence the code uses. That number is solid **for that store and must not be quoted as the current cost**: it is `3.008 x` its own 216,977,408-byte result, and the live store's result is now ~540 MB, so the same compaction costs **~1,616-1,626 MB today** - confirmed twice on the live daemon at `3.008` and `3.010 x post_size` (`E3-VACUUMRECON-65`, from `E3-ABHARNESS-59`'s retained series). **Budget the relationship, not either constant.** A budget quoting 652,726,272 B understates today by 2.48x; one hardcoding 1,616 MB is wrong the moment the store moves, and this store grew from 217 MB to 540 MB over the life of this queue. At today's result and the cadence already recorded here (3,600-7,800 s, 11.1-24.0 runs/day) that is **17.9-39.0 GB/day**, consistent with the 17.2-37.3 GB/day recorded at 514 MB. **The apparent 1.7-2.5x disagreement with the live measurement was store size and nothing else**: scaling the audit figure by `537,182,208 / 216,977,408 = 2.476` predicts 1,615,988,242 B against a measured 1,615,863,808 B, agreeing to **0.01%**. This is the tenth and eleventh confirmation of the same constant, the first two on data this queue did not produce. **Two measurement cautions for anyone re-deriving it.** The whole cost lands in a sharp **five-to-six second burst** straddling `last_vacuumed_at`, against traffic of 0.6-17 MiB/s either side, so a per-run figure must be **burst-bounded, not window-bounded** - a fixed `[t-30, t+3]` window clips the tail and reports 2.020x instead of 3.010x, which is exactly how a 1,092 MB low end arose, while a naive 20x-baseline detector overshoots to 3.235-3.467x by sweeping in 400 s of unrelated traffic. And **the `byte_step` detector multi-counts**: it re-reported one compaction five times over with identical `db_bytes_before 596,357,120` / `db_bytes_after 537,182,208` on consecutive polls while the file simply sat at its post-vacuum size. **Count events with `service_timestamp`**, which reads `schema_meta.last_vacuumed_at` and fires exactly once per successful rewrite; `byte_step` is fine for sizes and useless for counting, and dividing a total by its count understates per-run cost roughly threefold. **Still unexplained and deliberately not chased:** the constant was 2.008 rather than 3.008 in one of nine earlier runs and has never recurred; settling it needs an instrumented `VACUUM`, which the freeze forbids and which is not worth the window. Use 3.008 - it is the observed norm and the conservative direction.

**`freelist_count` is not the guard input, and an earlier revision of this file was wrong to treat it as one.** The premise "`freelist_count` is ~0, therefore there is nothing to compact" does not hold. The audited copy had `page_count` 54,917 and `freelist_count` **0**, and compaction still shrank it from 224,940,032 to 216,977,408 bytes - **7,962,624 bytes, 3.5399%**. The current live store reads `page_count` 135,595 and `freelist_count` 0 and tells you nothing more. `freelist_count` counts *fully free pages only*; it cannot see unused space *inside* live pages, which is what that 3.54% was. A guard written as `freelist_count / page_count < threshold` would have skipped a database that demonstrably shrank.

So the guard needs a compaction-benefit metric that detects intra-page free space. Candidate inputs, to be chosen by measurement, not by preference: `PRAGMA page_count` against the `dbstat` sum of live payload bytes; a periodic dry-run estimate; or a measured shrink ratio from the previous compaction used as the predictor for the next. **The guard input is an open decision, not a settled one** - do not implement a `freelist_count` guard.

This supersedes the earlier note in this file that "VACUUM is not the fix". The half that is established: the `VACUUM` that already runs is itself a major writer, 652,726,272 bytes per run. The half that is **not** established: that running a `VACUUM` cannot reduce steady-state write volume. No retained command measured append rate before versus after compaction, and the copy did shrink by 3.54%, so a smaller file plausibly touches fewer B-tree pages per insert. Measure it before repeating the claim.

"Hourly" is also shorthand. The next due time is completion plus `VACUUM_INTERVAL_SECONDS` 3600 plus up to `VACUUM_JITTER_SECONDS` 600 of jitter, and busy deferral extends it further. Use 3600-4200 s plus deferral, not 3600 s, in any daily model.

A composed model estimated 15.7 GB/day from this `VACUUM` and about 1.74 GB/day saved by changing CPU cadence alone. **Neither is a verified live 24-hour total.** The current production database measured 562 MB, so the older 21 GB/day model must not be quoted as current fact.

### Cause A1: fixed per-transaction overhead is ~93% of append volume

A single live-shape CPU record commit produced roughly **25.5 KB of WAL writes**. Fixed transaction overhead was roughly 23.4 KB of that: solving the one-row versus ten-row cost model gives **23,407.4 B fixed out of 25,144.4 B per one-row sample, 93.092%**. The primary owner is transaction *frequency*, not row count or payload size. The 93% figure is reproducible and is the load-bearing one.

**The "about 520x" multiple is withdrawn as unreproducible.** Rerunning the surviving `measure_writes.py` / `measure2.py` / `measure4.py` at source identity `feed729c9651112182b6161718b8156553ccdaec` wrote 26,460 B per commit and 25,537 B of WAL per commit against a `length(payload_json)` of **44 B**, giving **601.364x** and **580.386x** - not 520x. A 49-byte denominator would land near 520x, but no surviving artifact records a 49 B payload. Either cite the run that used a 49 B denominator and retain its output, or quote 601x/580x against 44 B. Do not keep quoting 520x.

Changing only the CPU acquisition cadence from one second to five, measured:

| CPU plus unchanged one-second `service_load` | 88,133 to 45,539 B/s, **down 48.3%** | 4.08% to 1.27% of one core, down 68.8% |

The gap between 87.2% and 48.3% is the point: `service_load` has its own `1,1` cadence and kept writing.

**CORRECTED 2026-08-25 by `E3-REMEASURE-08`. This paragraph previously concluded "Cadence per family is not the lever; merging families into one transaction is." That inference is wrong and is withdrawn. Interval is the lever; merging is a secondary multiplier that costs extra per commit.**

**Merging carries a measured penalty.** The one pair with equal commit count and equal fact count but different merge state - `per_family-i10` and `merged-i5`, both 720 commits of 10 facts - differ by **1.2505x: the merged commit costs 25.05% more**, because one transaction spanning two families dirties both families' index and coverage pages instead of one. The lane predeclared "commit count is the whole lever" and this falsified its own hypothesis.

**The previously withdrawn figures were right; only their evidence was missing.** Measured: **79.4091%** at a merged five-second transaction against the claimed 79.8774% (-0.4683 pp), and **87.6579%** at ten against the claimed 87.9971% (-0.3392 pp). The `93.092%` fixed-overhead share also reproduces, at **92.8150%**. **They may be cited again**, now against a retained artifact. Do not, however, size a design from the two-point linear fit: at five facts it predicts 70,603.5 B against a measured 76,512.7 B.

**A measurement trap that invalidates any harness ignoring it.** Appends only write `ring_invalidations` when they intersect a **published** ring slot, and no materializer runs in a harness, so a ring published at the start of an append window has a head that never advances and everything past the one-second ring's 300-slot horizon intersects nothing. A first grid recorded **zero** invalidation rows in every arm. With the ring head covering the window the baseline is **1.8524x** higher. **Any append-cost measurement taken with a static ring head understates real per-commit cost by about 46%.**

**Topology is worth 57%**: the same grid on a fresh empty store baselines at 251.322 MB against 394.863 MB on the realistic copy, confirming the fixed cost is a property of page, index and ledger depth rather than a SQLite constant. Per-commit cost is genuine WAL append volume, not writeback amplification - at about 24,494 B per commit against a 4,096 B page plus a 24 B frame header, **each commit dirties roughly 5.9 whole pages for a payload of tens of bytes.** That is what "fixed per-transaction overhead" physically is, and it is why commit count dominates.

**Implementation consequence: the disk saving does not require a cross-family merged transaction.** A per-family flush deadline at ten seconds delivers 83.53% with no cross-thread merged transaction, which removes the hardest part of the design - reconciling the worker's `publisher` (`service.py:2077`) with the listener's `self.writer` (`service.py:3579`) inside one transaction. Evaluate that simpler shape first.

### Cause A2: `ring_invalidations` has no retention

`RETENTION_SECONDS = 2 * 24 * 60 * 60` at `storage.py:61`, and `observations` obeys it through `DELETE FROM observations WHERE observed_at < ?` at `storage.py:3526`. No equivalent delete exists for `ring_invalidations` anywhere in `yolomux_lib/stats_current/`; a search for any statement removing rows where `applied_at IS NOT NULL` returns nothing.

Growth is 3,682 rows per hour and 55,621 per day, so 282,502 rows are roughly five days against a two-day window. Every row is `reason = fact_mutation`, spread across four resolutions: 1s 79,648, 10s 59,119, 60s 74,909, 300s 68,826. The table is the retention shadow of `observations`; pruning the facts while keeping their invalidation records forever means the derived table outgrows its source.

### Cause A3: a 2 MB cache against a 503 MB store

`cache_size` and `mmap_size` are never set anywhere in `yolomux_lib/stats_current/`, so SQLite's 2 MB default applies. 4.55 TB of logical reads against 641 MB of physical reads means pages are served from OS page cache, but each of those 1.2 billion hits still costs a syscall, and each insert re-reads B-tree pages it evicted moments earlier, dirties them, appends them to the WAL, then writes them again when `wal_autocheckpoint` fires at 1000 pages. Read the tension section above before changing either value.

`PRAGMA temp_store = FILE` at `storage.py:799` is a documented memory-for-IO trade, listed so a reader does not mistake it for an oversight.

## Closed - do not re-open any of these

- **The ring-invalidation churn fix works.** `7a5f751e1` is an ancestor of the running `014837508`, verified with `git merge-base --is-ancestor`. Of 282,502 rows only **71** are unapplied, so superseding and retirement behave exactly as the comments at `storage.py:1715-1737` describe. Keeping retired rows is stated there as intended; that intent is **Cause A2**, not a bug in the collapse logic, and not Cause A1. An earlier revision of this bullet said A1 and was wrong: A1 is fixed per-transaction overhead, while the retained rows are the unpruned-retention cause. Retirement working correctly is exactly why A2 exists - the rows are retired and then kept forever. Do not re-derive it.
- **The `_append_uncovered_gap` seek fix landed and is confirmed in situ.** `import bisect` and `bisect.bisect_right` at `materializer.py:2004`. It fell from 39% of process CPU pre-patch to 0.7%. Whole-service before/after was 55.9/55.7/55.3% base against 27.4/26.9/28.4% patched, about 2x, 33.4 to 16.5 CPU-s per 60s.
- **The load-sensitive timing gate was replaced with a deterministic one.** `_SeekOnlyGaps` at `tests/test_stats_current_materializer.py:1423` counts `__getitem__` accesses and raises on `__iter__`; it reads no clock, so it cannot flake with host load. Forced-red against the old full-scan implementation gave 3 failed. Never restore a threshold-on-duration gate here, and never raise a threshold, add retries, sleeps, serialization, or lower concurrency to make this area green.
- **JSON decode amplification is not the CPU driver.** About 2.7% of profile at `storage.py:2402-2530`. Disproved for CPU; it remains a candidate for memory only.

## Gotchas

- **A five-second CPU cadence does not make statsd a five-second writer.** `service_load` has its own `1,1` cadence. Any implementation or measurement that calls the result "five-second" while leaving that family unchanged is mislabeled, and the 48.3% versus 87.2% rows above are exactly that difference.
- **Do not** use `synchronous=OFF`, drop time indexes, suppress unchanged samples, tune WAL checkpoints as the primary fix, or shorten retention below the 24-hour range. Treat `usage_atoms` normalization as a later schema-migration follow-up, not the first write-reduction change.
- **Do not quote the composed daily-write models as fact.** The 15.7 GB/day `VACUUM` figure, the 1.74 GB/day cadence saving, and the older 21 GB/day model are all composed estimates. The current production database measured 561,655,808 bytes (561.656 MB).
- **These figures are withdrawn. "`freelist_count` is 0 so there is nothing to reclaim" (a `freelist_count = 0` copy shrank 3.5399%).
- **`freelist_count` cannot answer "is compaction worth it".** It counts fully free pages, not unused space inside live pages. Any guard, dashboard, or log line that reports compaction benefit from `freelist_count` alone is reporting a number that does not mean what it says.
- **Do not restart 7770 to test any of this.** It is production and off-limits until Keiven says otherwise. Measure on 7771 or a disposable port and report 7770 by observation only.
- **statsd respawns from disk.** It runs `--idle-seconds 60.0`, exits when idle, and picks up new module code with no listener restart. The listener process is separate and keeps running old in-process code, so a port restart changes the listener's code, not statsd's. Never attribute a post-restart improvement to a statsd patch: restart hygiene alone drops caches, resets the WAL, and re-derives generations. The clean separator is a restart onto a SHA without the patch, sampled identically.
- **`/api/ping` carries no version field**, and the seek patch's own correctness evidence is byte-identical fixture output, so no served response can distinguish patched from unpatched. Prove the running module by `.pyc` timestamp and size validation against the on-disk source.
- PSS is the aggregate denominator; summing RSS double-counts shared pages. Track peak and steady USS separately because the incident process was almost entirely private anonymous memory.
- A 503 MB SQLite file does not explain RSS by mmap when measured `mmap_size` is zero and file PSS is 0.2 MiB. See the tension section before touching cache or mmap for a memory reason.
- The three deleted SQLite TEMP files totalling 64.3 MiB were disk-backed and unmapped. They affect disk and IO, not anonymous PSS.
