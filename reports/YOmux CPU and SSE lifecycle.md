The strongest measured CPU cause was Finder's recursive watch-signature scan: a 30-second Go profile sampled 133% of one core, with Finder walks accounting for 74.52% cumulative time. ## Finder rescanned overlapping roots every half second

A 30-second Go profile recorded 39.92 CPU seconds. finder.Service.walkDescriptors.func1 accumulated 29.75 seconds (74.52% cumulative), while Linux Syscall6 used 17.61 seconds flat (44.11%). The source path matches: Finder's watch loop called recursive signature polling every 500 ms, and each directory signature enumerated descriptors, up to the native watcher limit of 4,096 entries. The browser state watched overlapping roots under /home/keivenc, /home/keivenc/dev, and /home/keivenc/dev/yomux, so a change or poll could traverse the same tree multiple times. ([Finder watch loop](/home/keivenc/dev/yomux/yo7111/internal/finder/service.go:1338), [fallback poller](/home/keivenc/dev/yomux/yo7111/internal/finder/service.go:1452), [recursive directory signature](/home/keivenc/dev/yomux/yo7111/internal/finder/service.go:1657), [descriptor walk](/home/keivenc/dev/yomux/yo7111/internal/finder/service.go:178), [profile](/tmp/yomux-yo7111-no-collectors.pprof))

The fix retains lease pruning and runs recursive signature fallback only when native watching is unavailable or degraded, or when a signature path is not covered by its native watch root. When native watching is healthy but has uncovered paths, it scans only those paths; a closed event stream remains degraded, and degraded fallback runs every five seconds. This preserves fallback coverage while removing repeated full-tree polling where kernel events cover the paths. TestWatchPollingFallbackRunsOnlyWhenNativeWatchingIsUnavailableOrDegraded passed, including the uncovered-path case. Earlier 15-second measurements were 15.1% before and 10.5% after a restart, but the workloads were unmatched. The latest process averaged 16.35% over a 20-second `pidstat` sample, with one-second samples ranging from 1% to 98%. These samples do not quantify the fix's effect; a fresh stack profile is blocked because `perf_event_paranoid` is 4, and the HTTP diagnostics returned 401 without a session.

Stats remains a secondary cost. The profile attributed 5.42 seconds (13.58%) to tagged stats components: lifecycle 6.69%, token collector 5.29%, host collector 1.30%, and agent status 0.30%. The Finder 74.52% number is cumulative and includes descendants; it should not be added to flat percentages. SQLite C calls also appeared prominently, but the profile did not identify the originating SQL statement. The profile named no-collectors was not a collectors-off sample: bare STATS_DISABLE_COLLECTORS=1 is ignored. The accepted names are YOMUX_STATS_DISABLE_COLLECTORS and legacy YOLOMUX_STATS_DISABLE_COLLECTORS, and collectors were enabled. ([collector check](/home/keivenc/dev/yomux/yo7111/cmd/yomux-go/main.go:847), [environment prefixes](/home/keivenc/dev/yomux/yo7111/internal/productenv/namespace.json))

## Stats lifecycle runs every second and stores millions of rows

At startup, the stats lifecycle starts on a one-second cadence before the collector-disable check. Disabling collectors therefore leaves reconciliation, materialization, and projection refresh running. When enabled, host CPU collection runs every five seconds, memory every minute, disk every five minutes, agent status every ten seconds while active and every minute while idle, and token collection defaults to every five seconds. Token and status collectors share the machine-wide agent inventory to avoid repeating that process census. ([lifecycle cadence](/home/keivenc/dev/yomux/yo7111/cmd/yomux-go/main.go:808), [collector setup](/home/keivenc/dev/yomux/yo7111/cmd/yomux-go/main.go:879), [host collection](/home/keivenc/dev/yomux/yo7111/internal/stats/host_collector.go:134), [token collection](/home/keivenc/dev/yomux/yo7111/internal/stats/agent_tokens.go:28))

Read-only SQLite inspection found 2,442,942 observations, including 2,141,210 service_load rows. The database was 1.47 GB and its WAL 5.45 MB. Retention is 48 hours, with pruning once a day; a row can remain nearly 72 hours until the next prune. This explains why some rows were about 54 hours old. Stats consumed about one-seventh of sampled CPU at the profiled peak, enough to merit follow-up but insufficient to explain the green dashed spike. Authenticated live diagnostics were unavailable, and there was no matched collectors-off profile or query-level SQLite trace, so exact lifecycle steady-state CPU and expensive statements remain unmeasured.

The browser capture also showed 11 settings requests totaling about 1.32 MB and 51 /api/stats-refill GETs in 53 seconds. Settings repeatedly fetched heavy metadata when a response marked it deferred but had an unchanged revision; the client now clears the deferred flag before the equal-revision return. Refill polling ran every second while work was queued or active; idle polling now backs off to ten seconds, with busy polling still at one second. The GETs averaged 24.2 ms and returned only 13 KB total. These patterns explain avoidable browser/network work, not the measured CPU hotspot. ([settings metadata handling](/home/keivenc/dev/yomux/yo7111/static_src/js/yomux/50_editor_settings_runtime.js:1355), [refill polling](/home/keivenc/dev/yomux/yo7111/static_src/js/yomux/84_stats_current.js:1711))

## SSE is moderate, with an oversized reconnect snapshot

The supplied 53-second capture reports 92 SSE frames (1.74 per second) and 218,846 bytes (4.13 KB/s). Forty `fs_changed` and forty `files_changed` frames are 40 event pairs, or 0.75 pairs per second; the first refreshes the file explorer, the second open files. Separate overlapping watch records can also produce close-together pairs, but the capture omits payload paths and client IDs, so it cannot establish duplicate reporting. This rate and byte volume are modest and do not explain the earlier 133%-of-one-core profile. ([Finder event publication](/home/keivenc/dev/yomux/yo7111/internal/finder/service.go:1435), [browser event handlers](/home/keivenc/dev/yomux/yo7111/static_src/js/yomux/99_client_event_transport.js:701))

The 142,870-byte ready frame accounts for 65.3% of all SSE bytes. It carries resource revisions, not file contents. Revision keys accumulate independently of the 256-event history cap; a read-only persisted snapshot had 1,366 keys and a compact 68 KB revision map. That proves a growth mechanism, but does not reconstruct the exact captured frame. The eight background_refresh_done frames were retained replays. Their 6.4–37.9 minute values measure event age at receipt, not delivery time; the debug label now says “age at receipt.” A replay can cause cache-only session-file revalidation on a fresh client, but the capture does not prove those events caused its ten session-file refreshes. ([ready snapshot](/home/keivenc/dev/yomux/yo7111/cmd/yomux-go/main.go:2727), [revision history](/home/keivenc/dev/yomux/yo7111/cmd/yomux-go/event_operations.go:1088), [age label](/home/keivenc/dev/yomux/yo7111/static_src/js/yomux/85_debug_panel.js:5260))

The trace has no EventSource URL, channel, subscriber count, or broker counters; authenticated diagnostics returned 401. It therefore cannot tell whether that ready frame came from the general event stream or stats stream, or quantify fanout and coalescing. The steady event rate and bandwidth are modest, but the 143 KB ready snapshot is a costly reconnect outlier that can be bounded or pruned.

## UI labels and display mismatches are corrected in the rebuilt bundle

Names beginning __yomux_view_ are internal cloned tmux sessions used to expose individual windows as distinct views. They should not appear as user-facing session names. The UI resolves view labels to the original source session/window name, and historical stats aliases map internal IDs back to the original tmux name so windows with the same name merge into one token history group. This aliasing affects historical token labels only; it neither renames real tmux sessions nor changes the CPU chart. ([view ID prefix](/home/keivenc/dev/yomux/yo7111/static_src/js/yomux/00_bootstrap_state.js:229), [alias normalization](/home/keivenc/dev/yomux/yo7111/static_src/js/yomux/84_stats_current.js:2597))

## Conclusion

The earlier green dashed peak has a source-backed explanation: recursive Finder fallback scans dominated the profile, while stats was a secondary contributor and measured SSE traffic was too small to explain that peak. The current source avoids scans where healthy native watches provide coverage, but current short CPU samples still contain intermittent spikes and no post-fix profile was available. A matched browser and filesystem workload with an authenticated profile is needed to measure the fix's effect and identify the latest bursts. Remaining performance work is to profile stats and SQLite under controlled Finder load, and bound the revision map so reconnect snapshots do not grow indefinitely.
